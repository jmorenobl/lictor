# AGENTS.md

Guidance and operational constraints for AI agents working on **Lictor**.

## Project Overview

Lictor is a deterministic harness and agentic runtime that implements Gherkin acceptance scenarios using an autonomous coding agent, systematically verifying each implementation through strict multi-level quality gates (L1–L5).

- **Language / Runtime:** Python >= 3.12 (managed via Astral `uv`)
- **Core Architecture:** Hexagonal Architecture (Ports and Adapters) enforced with `import-linter`
- **Primary Dependencies:** LangGraph, Pydantic v2, Typer, `gherkin-official`, `defusedxml`

> **Known limitations:** a green commit doesn't yet withstand an adversarial agent. It is the exact tree that passed in a clean clone, with no user configuration involved, and the agent no longer works in the project: it gets a copy with no `.git` and no `.lictor/`. That closes the routes that go through the agent's working directory, not the rest: it runs as your user, so with an absolute path it can reach `.git`, `.lictor/`, the verification environment, `~/.netrc` and the interpreter. Those writes are detected and undone while Lictor is alive (`IntegritySnapshot`, the environment hash) and refuse a resume after a kill (the anchor in the checkpoint), unless the checkpoint is rewritten as well. A process the agent leaves behind can plant in the environment between `prepare` and its hash, and the hash then vouches for it (`test_nothing_planted_during_the_build_is_trusted`). Separately, any project code imported during the tests runs in the runner's process, so it can alter the runner as well as forge the report, the properties of the outcome plugin included (`test_c6`). No phase of this plan closes those two: they stay as strict `xfail` until the sandbox of increment 4, and until then a green doesn't withstand an adversary. The `c4` and `c4b` cases only close specific routes: an installed plugin, `src` in the interpreter's startup path (`sitecustomize`), a package in `src` replacing a dependency, and inherited variables. They don't close `c4` in general.

## Essential Commands

All commands are executed using `uv`. Always run them from the repository root.

### Environment & Dependencies
```bash
uv sync --all-groups       # Install all dependencies including dev tools
```

### Quality Gates & Static Checks (L1 & L4)
```bash
# Code style and formatting (L1)
uv run ruff check .
uv run ruff format --check .
uv run ruff format .       # Automatically format code

# Strict typechecking (L1)
uv run mypy --strict src scripts

# Architectural boundaries check (L4)
uv run python scripts/check_architecture.py
```

### Testing & Verification (L2, L4 & L5)
```bash
# Fast unit tests (L2)
uv run pytest tests/unit -q

# Integration & architecture tests
uv run pytest tests/integration -n auto -q

# Same, without the slow audit reproduction cases
uv run pytest tests/integration -q -m "not repro"

# What every platform runs in a pull request (about 2 min), and what a PR runs of repro
uv run pytest tests -n auto -q -m "not repro"
uv run pytest tests -n auto -q -m "repro and not exhaustive"

# Coverage enforcement (L4 - minimum 90% branch coverage) of everything but repro, as the
# `coverage` control of lictor.json runs it; the nightly measures the whole number, repro included
uv run pytest tests -n auto -m "not repro and not exhaustive" --cov=lictor --cov-branch --cov-fail-under=90 -q

# Domain purity test coverage (L4 - minimum 95% domain coverage)
uv run coverage report --include="*/lictor/domain/*" --fail-under=95

# Security audits (L4). `uvx pip-audit` alone would audit its own environment, not uv.lock
uv run python scripts/audit_dependencies.py
gitleaks detect --no-banner

# Mutation testing (L5); the script also leaves the score where the `mutation` reader reads it
uv run mutmut run
uv run python scripts/mutation_score.py mutants/score.json

# Every control of lictor.json and the acceptance (the repro cases), in a clean clone, in the real
# verification environment; without --keep-going it stops at the first blocking failure. Each test
# runs once: `coverage` runs everything but repro, and the acceptance only repro. Without --level it
# takes as long as the whole suite: it is for measuring, not for closing a change
uv run lictor check --keep-going [--control <id> ...]
```

### Running a Subset
```bash
uv run pytest tests/unit/test_routing.py::test_route_load_spec_seal_ok -q   # Single test
uv run pytest tests/unit/test_routing.py -k verify -q                       # By keyword
uv run lictor check --level L1,L2                                           # Gates from lictor.json
uv run lictor check --control types --control unit                          # Some controls by id
```

`lictor check` runs the controls in `lictor.json` plus the acceptance suite (`--control acceptance`), as a run would, and also the controls with `"stage": "check"`, which a run leaves to it: see «`lictor check` verifies what `run` would» below. Lictor's own `mutation` and `audit` are `check`, so a run doesn't pay them in each attempt; `--level L1,L2,L4` still runs `audit`. The `coverage-domain` control reads the `.coverage` file left by the `coverage` control in the same clone, so it depends on that one running first in the same `check`.

### What to run and when

The CI gives the green. Locally, run what fails fast, once; never the whole of `repro` or `lictor check` without `--level` before a pull request (that took over 45 min, and the CI repeats it).

- **While editing:** the test file you are working on (`uv run pytest tests/unit/test_x.py -q`), `uv run ruff check <files>`, and `uv run mypy --strict src scripts` if a type changed.
- **Closing a change, once** (about 2.5 min):
  ```bash
  uv run lictor check --level L1,L2,L4     # lint, format, types, unit, architecture, coverage without repro, audit, secrets
  uv run pytest tests -n auto -q -m smoke  # the 8 cases with the whole configuration of `lictor init`
  ```
- **Repro:** only the exact case (`uv run pytest <node id>`), to reproduce a failure of the CI. The files go by audit phase, not by area, so there is no «repro of the area».
- **Several agents on one machine:** `-n 4` instead of `-n auto`, or they slow each other down (F45).
- **The whole `tests` at once** (`uv run pytest tests -n auto`, as the nightly does) needs `--dist worksteal`: the `repro` cases are collected first, and with the default distribution each worker starts with a run of consecutive tests, so one worker got every `repro` case and ran them one after another while the rest sat idle (macOS went from 36 to over 90 min). A run of `-m "not repro"` or of only `repro` doesn't need it.
- **A new test slower than 10 s** needs the `repro` mark and a reason: something only seen with everything set up. The CI lists the others as warnings.

Budget, measured in the CI. Going over is an issue, like a broken test. `scripts/ci_budget.py` holds the CI's figures and warns, never fails; `timeout-minutes` is only the cut against a hung job, about 2.5 times what a job takes.

| When | Budget |
|:-----|:-------|
| While editing | < 30 s |
| Closing a change, locally | < 3 min |
| Pull request, critical path, without the queue | < 12 min |
| Each job of the nightly | < 60 min |
| Mutation | < 5 min |

## Architectural Boundaries (.importlinter)

Lictor strictly enforces hexagonal architecture layers. Dependencies only point inward:

```
[CLI / Bootstrap]
       ↓
[Orchestration (LangGraph)]
       ↓
[Application (Use Cases & Ports)]
       ↓
[Domain (Pure Models, Rules & Routing)]
```

### Layer Contracts & Rules:
1. **Domain Purity (`lictor.domain`):**
   - Zero framework or adapter dependencies.
   - **Forbidden imports:** `lictor.adapters`, `langgraph`, `typer`, `pydantic`, `defusedxml`, `gherkin`.
   - Contains pure Python dataclasses, business rules, routing algorithms, and domain error definitions.
2. **Application Layer (`lictor.application`):**
   - Coordinates domain models and defines ports (`lictor.application.ports.py`) via `typing.Protocol`.
   - **Forbidden imports:** `lictor.adapters`, `langgraph`, `typer`, `pydantic`.
3. **Orchestration Layer (`lictor.orchestration`):**
   - Composes LangGraph state graphs and workflow nodes.
   - Receives adapters already instantiated via dependency injection from `lictor.bootstrap`.
   - **Forbidden imports:** `lictor.adapters`.
4. **Adapter Independence (`lictor.adapters.*`):**
   - Adapters (`agents`, `vcs`, `runner`, `readers`, `spec`, `store`, `config`) implement application ports.
   - Adapters must never import from each other.

## How a Run Works

`lictor run` drives a 14-node LangGraph graph (`orchestration/graph.py`), and each scenario moves through `pick_next → implement → verify → commit | quarantine`, and after `commit` through `refactor → verify_refactor → commit_refactor` (ADR-0010). The pieces that interact:

- **Routing is split.** Most conditional edges are pure functions in `domain/routing.py`, tested without a graph. A few trivial ones are closures in `create_graph`. Graph state is a flat serializable `TypedDict`; nodes convert to and from domain types at the boundary (ADR-0003).
- **Git is the source of truth for green scenarios, and for what they were green for.** `SpecHistory` (`application/spec_history.py`) takes, for each scenario, the most recent commit whose `Scenario:` trailer names it, and hashes that scenario in the features of that commit's own tree (`GherkinSource.spec_hashes`, cached by commit and file). `classify_scenarios` compares it with the current hash: `green`, `reopened` if it differs or isn't found, `new` without a commit. The hash (`spec_hash`) covers steps with their kind, doc strings, tables, backgrounds and examples, not names, tags, comments, spacing or the keywords' language; the form is Lictor's own, so a new `gherkin-official` reopens nothing. There's no hash trailer and nothing to migrate. `load_spec` classifies before `build_driver`, so the driver's prompt lists the greens and asks to update the reopened ones (`scenario.reopened`); `CheckRed` classifies again from git, not from the checkpoint. Changing commit messages or trailers can break resume.
- **The red is judged by class** (`judge_red`). A green must pass. A pending one, reopened or new, must fail with a valid red, and what happens when it passes depends on the driver. With the sealed driver its test was proved when it was sealed: a reopened one is registered again without the agent (as when the scenario wasn't found in its green commit's tree: a change to `features/` breaks the seal) and a new one is a collateral green. With a fresh driver nothing tells a pass from a vacuous test. A new one is `unproven`, and the impostor of the interface tries to prove it (ADR-0011, `_prove_or_reject`); see «A new scenario the code already meets is proved, not assumed» below. Proved ones are registered after the seal, in the same `advance_head`; any other rejects the driver as `sin_prueba`, retryable when the agent can fix the test (`InterfaceProof.fixable`: it never called the interface, it passed with an altered result, or it failed but not by its own assertion), and final at once, exit 10, when no retry changes what the impostor can tell (nothing it returned could be altered, a run told nothing); when attempts run out the stop says first to fix the test and then, if the code already met the scenario, to register it with `lictor register <ids>`. A profile without `interface_impostor` keeps the old rule: retryable, with a message that claims nothing. A reopened one is `respecified`: the step may still hold the old value, so the run stops with exit 10 without retrying (`especificacion_cambiada`), and a person who knows the change was only wording registers it with `lictor register`; the impostor never runs for it. So nothing is registered inside `red_check` before the seal, and only what the impostor proved after it. What passes without the agent goes into one empty commit on top of HEAD (`Scenario:` for each, `Lictor-Collateral` for collaterals; its subject names one scenario or counts several, `registration_subject`), with `scenario.reregistered` or a collateral `scenario.green`. Every `scenario.green` names the commit whose `Scenario:` trailer names it: after `VerifyAttempt`, the implemented scenario's is the parent of the collateral one the branch moves to.
- **The profile declares what makes the oracle valid** (`oracle`, only in the profile, read by `resolve_defences`). `link: "scenario"` maps each test to the scenario it executed, as the plugin `lictor_outcome` reports it in JUnit properties (`lictor.scenario`, `lictor.feature`); a name that contradicts it, or carries an ID without executing it, rejects the driver, and so does executing it from any file but the scenario's own (`Scenario.file`, passed to `map_test_cases_to_scenarios` as `files` by `CheckRed` and `VerifyAttempt`): pytest-bdd reads a copy with the same tag even if it isn't a `.feature`, which `load_spec` never loads. `red_kinds` lists the failures that count as red: `lictor.failure` is `assertion`, `not_implemented` or `error`, decided by the exception's class in the plugin, never by its text, and `not_implemented` also needs `lictor.origin` in `paths.writable` outside `paths.driver` (`red_failure_problem`). `interface_impostor` proves a new scenario that already passes with a fresh driver (see below). `impostors` reruns the acceptance of a fresh driver in clones where each matching line becomes each replacement, `{code, name, double}`: in `python-uv`, `return None`, `return True` and the two doubles of `python_uv/lictor_doubles.py` (`ONE` and `EMPTY`, see «The stubs' impostors ask for an assertion of a Then» below). Evidence goes to `NNN-red/impostor-<n>/`. A fresh driver with tests of no scenario is rejected (`sin_escenario`). Without `oracle` the old rules apply: any failure is red and tests map by name. The plugin runs in the process under test, which can forge it as it can forge the report (`c6`).
- **A new scenario the code already meets is proved, not assumed** (ADR-0011, F58, `domain/interface_proof.py`). The profile's `oracle.interface_impostor` names a variable (`LICTOR_IMPOSTOR`, which `reserved` covers through `LICTOR_*` and the `Profile` validator checks), a control mode and the modes (`mas`, `menos`). `CheckRed._prove_interface` runs the acceptance once per mode, each in a clean clone of the candidate and inside `IntegritySnapshot`, passing the variable through `VerificationEnvironment.run(extra_env=)` as JSON with the mode, the absolute `writable` and `driver` roots of that clone, the stubs it must leave unwrapped (`stubs`, file → lines, empty here) and the steps to alter (`steps`, the domain's `ALTERED_STEPS`: `when` and `then`; the plugin has no default and fails to load without it); evidence goes to `NNN-red/interfaz-<modo>/`. The plugin `python_uv/lictor_impostor.py` (in `verification.files` and `plugins`, idle without its variable) installs a `sys.meta_path` finder when it loads, so it wraps each module of `writable` outside the driver as it is executed: a driver that did `from paquete import f` would keep the original if it wrapped later. It wraps functions, coroutine functions and non-dunder methods, static and class methods and property getters, never classes or generators (a coroutine's caller is the frame that creates it, not the loop; it counts once awaited, from the step it was created in, and its result is altered when the `await` ends; before 3.12 only `asyncio.iscoroutinefunction` still sees the wrapper as one); an altered value the driver hands back to the interface goes back real, if it is immutable and not one Python shares (a list the driver changed is its own); what reaches the interface for the driver through a library is counted and never altered: `lictor.interface.via` when the project calls it after the driver entered it through a library (typer keeps the command it decorates before the impostor wraps it), `lictor.interface.handed` when the library calls what the driver handed it, both by step, and `lictor.interface.entry.<step>` names the first library from the driver outside the standard library (what Python generates for a project module, as a dataclass's `__init__`, is the project's, and a coroutine the project created walks from its creator, not the loop; ADR-0011, amendment of coroutines and libraries); a call whose caller's file is in the driver runs the real function and, but in the control and only when made from a step `steps` names, alters its result (B: what a Given, a fixture or code outside a step gets stays real; a fixture counts as outside even when a When requests it, because pytest-bdd resolves a step's fixtures inside the step, so `pytest_fixture_setup` marks it) (`alter`: number ±1, a `date` or `datetime` ±1 day (ADR-0012), `bool` negated, text or collection one element longer or shorter, `None` for a sentinel (`AlteredByLictor`, which also fills an empty collection), anything else left alone and not counted; an exception swallowed in `mas`, replaced by `ImpostorError` in `menos`. A list or tuple changes at its start with an element of its own form, so a test of its first element or of each element's attribute fails by its assertion: `mas` puts the last one in front, altered if its kind is known, and `menos` drops the first; a dict in `mas` gains a key with such a value. Its tests table, `_CHECKS` in `test_lictor_impostor.py`, fixes what each way of checking a list proves; `[-1]` and the first of a list of one are known limits). It reports `lictor.interface.calls` and `lictor.interface.altered` per test, and the same by step (`.given`, `.when`, `.then`, from `pytest_bdd_before_step`; outside a step only the total counts them), and `lictor.interface.altered_none`, the altered results that were None (an order's). `lictor_outcome` adds `lictor.step`, the kind of step that raised the test's failure (kept in `pytest_bdd_step_error` and written in `makereport` only for that same exception, so an `xfail` in a step counts nothing), `lictor.frame` (the file of the last frame inside the project, the test's own when pytest raises for it), `lictor.line` (that frame's line) and the kind `impostor`, by the exception's class. `interface_proof` (domain) proves a scenario only if its test passed in the control having called the interface from a When or a Then and, in every mode, had a result altered and failed by an assertion of a Then whose frame is in `paths.driver`, or by the impostor's error in a When or a Then (ADR-0011, amendment B); a run that crashed or didn't map proves none, and so does a mode that altered what a Given or a fixture got. The outcomes: `no_llama` (no call, only from a Given: detail `dado`, or only through a library that called what the test handed it: detail `entrega`, with `libraries`), `sobrevive`, `no_aserta`, `fuera_del_entonces` (an assertion of the driver in a Given, a When or outside a step, its message in the detail), all four retryable, and `sin_alterar` (nothing altered from the When on, or only an order's None, with the test passing), `a_traves` (from the When on it only reached the interface through a library that entered the project: the person reads which, `through_note`; in the stubs it is rejected as `sin_codigo`) and `no_concluyente`, final. The message of `sin_alterar` only tells the agent not to change that test, since it reads it when another scenario is retried; why the impostor couldn't judge it (`unalterable_note`) goes only where no agent reads it, the final rejection or the last attempt. `no_aserta` names the exception, the step, the file and line and the mode, and says the other value is Lictor's and the test mustn't handle it apart: with the file alone, the agent moved its steps out of it. A test that ignores the result, or checks it weakly (`assert x`, `is not None`, `isinstance`, `!=`, `pytest.raises(Exception)`, two calls compared), survives. All of them must be proved or nothing is registered: once sealed, the next red would register an unproved one as a collateral. The proved ones go in one empty commit on top of the driver's (`Lictor-Collateral: <driver>`, `Lictor-Proof: interfaz`, subject «ya se cumplía»), with `scenario.green` carrying `collateral: true` and `proof: "interface"`, and `driver.sealed` lists them in `already_met`; `RunProgress` (`already_met`), `status` and `report.md` («Ya se cumplían», «verde (ya se cumplía)») count them apart. It proves the test reads the result, not that it compares it with the scenario's value: a driver that copies what the code returns into the assert passes it (`@known_limitation`, until a semantic judge of the driver, phase 2c of the roadmap). **What the red check saw, and what C would say, is measured** (`domain/driver_measures.py`): `CheckRed` writes `lictor.driver.measured.v1` once per red check of a fresh driver, after its impostors and before `driver.sealed` or `driver.rejected`, so a rejected driver is measured too. It names its step (`step`) without hashing it, because the rejection still writes `error.txt` there; the dedup of `report.md` keys it by that path. It holds, per scenario, how each pending test failed at the red (`red_measures`), how it fared with each stub constant, named by `impostor_name`, and what C would say (`rule_c`: a Then's assertion of the driver, not applied), and what the interface proved (`outcome`) with its counts by step, the step each mode failed in and what reached it through a library in the control (`via`, `handed`, `libraries`; a column of «Medidas del driver»), the baseline for F62 and the impostor of the Gherkin. `report.md` shows them in «Medidas del driver»; no verdict, prompt or message reads them. The stubs' impostors count their stubs first: with none they don't run, and `driver.sealed` says `stub_impostors: 0` instead of passing them; a new test that fails by `NotImplementedError` with no stub to replace is refused as `impostor`.
- **The stubs' impostors ask for an assertion of a Then** (ADR-0012, F64, `domain/stub_proof.py`). Each constant runs the whole acceptance in a clean clone with every stub replaced (`CheckRed._run_stub_impostors`); a run that crashes or doesn't map counts for no test, one that kept a stub rejects the driver (`impostor_problem`: write it on one line), and if every run told nothing the driver is rejected. `stub_proof` judges each new pending test by what each constant reported (`caught`): if it passes with every plain constant, or with the first one (the no-op, `return None`), it goes to the impostor of the interface; otherwise it is accepted only if some constant made an assertion of the driver fail in a Then; else it is rejected as `fuera_del_entonces`, `sobrevive` or `no_aserta`, with the step, the line and the constant (a double's failure named first), all retryable. The doubles are what let a right test reach its assertion: `ONE` (true, one element, yes to every order) and `EMPTY` (false, empty, no to every order) answer an attribute, an index, a call or an arithmetic operation with a child of their kind (one per name and key), equal nothing but themselves, give `nan` to `float()`, an unlikely number to `int()` and their repr to a format, copy and pickle as themselves, have no special names, and end: deeper than `DEPTH` or past `BUDGET` operations in a test (the module is also a plugin, only to reset that count per test) they raise `LictorDoubleExhaustedError`. Without them C rejected 9 of 347 right tests of the passes; with them, none. Every constant but the first goes through `lictor_doubles.stub(name)`, which gives None when called from an `__init__`, the only value Python lets it return: with `True` or a double there the object couldn't be built in a Given or a When, no test reached its Then and the driver was rejected whatever its tests (F68, `test_v0_14_1_init_stub.py`). What goes to the interface runs `_prove_interface` with `_ToProve(stubs_at=<first constant>)`: each clone has its stubs at `return None`, evidence in `NNN-red/stubs-interfaz-<mode>/`, and the plugin is told their lines (`stubs`) and leaves those functions unwrapped, since what a stub returns is Lictor's constant (with them wrapped, `r in (None, True)` was proved). `stub_verdict`: `probado` accepts; `sin_alterar` (it called code that already exists, nothing alterable) accepts unchecked, in `driver.sealed` as `stub_unchecked` and in `report.md` («Tests aceptados sin comprobar», `unchecked_note`), never told to the agent; anything else rejects with the interface's message headed «pasa aunque los stubs no estén implementados» (`stub_reason`), but `no_llama`, which there means nothing it checks comes from code that already exists, has its own (`sin_codigo`): «no llama» would deny a When that calls a stub, and a profile without `interface_impostor` rejects it too. Once the attempts run out, `STUB_LIMITS_NOTE` tells the person the known forms no constant can prove (converting the result, `x not in r`, unpacking). No message asks for a check in a Given (F64 → F63). `lictor.driver.measured.v1` keeps per test `by_constant`, `outcome`, `interface` and `verdict`. The tables of `test_lictor_doubles.py` (89 right and 33 weak ways of checking) fix what C decides of each; a weak one rejected before C, because it passes with None and True, is never accepted.
- **A refactor follows each implemented green** (ADR-0010). `route_commit` sends `commit` to `refactor` when `lictor.json` leaves `refactor.enabled` on (the default; `init` doesn't write it, and it is in `config_fingerprint`), and only `commit` goes there: a collateral, a registration or a re-registration changed no code. `RefactorScenario` makes one call in a fresh copy of HEAD, through `AgentTurns` (`usecases/agent_turn.py`, shared with `ImplementScenario`), with `prompts/refactor.md`: the scenario, the paths its green commit changed (`Vcs.changed_paths`), the profile's `refactor_hints` (only in the profile, like `driver_hints`: `Defences.refactor_hints`, and a `lictor.json` with them exits 10, `refactor_hints_message`) and every `agent_run` whose plugin loads, minimum or not (`refactor_measures`). It has one attempt and spends none of the scenario's: a backend that fails pauses or repeats the call (`route_refactor`, as `build_driver`), and `settled_without_verifying` (domain `refactor.py`) ends a call before any verification: `rejected` is discarded, a finished turn with no change is `unchanged`, one cut short with no change is discarded (`L0-sin-cambios`). Any other tree goes to `verify_refactor`, which is `VerifyAttempt` with `role="refactor"`: `L0-sello` too, its candidate is `refactor(<ID>): mejorar el código sin cambiar el comportamiento` with `Lictor-Run` and `Lictor-Refactor-Of` and no `Scenario:` (so `SpecHistory` keeps the green's commit), `acceptance_failure` has no target (only the greens, its own among them), and `refactor_regressions` fails it at `L0-regresión` when a JUnit control passes fewer cases, a scored control leaves more untested, or a complexity control leaves more above its limit, than in the green's verification (`oracle_measures`, kept in the state as `refactor_baseline` by `verify`): without it a refactor could delete the unit tests, since `unit` passes empty and `python-uv`'s coverage only measures. What a score leaves untested is a count (`score_misses`: lines and branches not run, tried mutants not killed), never the percentage: removing covered code lowers the percentage and leaves untested exactly what was, and that is the simplification a refactor is for (F61). The refactor's prompt says what its green left untested (`refactor_measures_text`, from `refactor_baseline`) and what to do if it rises (it split or moved code the green didn't cover: cover it or don't split it), and `python-uv`'s `coverage` measures with `python_uv/lictor_coverage.py`, which counts as `score_misses` and, with the green's report Lictor copies next to it (`coverage-del-verde.json`, from the verification the state names in `refactor_baseline_step`), names where it rose and fell, its counts and the green's on its last line (F71). A pending scenario its tree turns green is a collateral, chained as in an attempt and marked `after_refactor`. `commit_refactor` (`CommitRefactor`, not `CommitGreen`, which would mark the scenario green again) advances with `advance_head` and pauses as `commit` on a blocked branch. A refactor never feeds `failures` or `rejected_paths` and never quarantines. It reuses `attempt_tree` and `last_verify`, so a resume accepts its candidate like an attempt's and its kill points fit the existing classes; the state adds `refactor_of` and `refactor_outcome`. `lictor.scenario.refactored.v1` says `applied`, `discarded` (with `failed_at`) or `unchanged`; `agent.*` carry `role: "refactor"`, `verify.finished` carries `role` for both, and evidence is `NNN-refactor.json` and `NNN-refactor-verify/` beside the green's attempt. `RunProgress`, `status` (`--json` adds `refactor`) and `report.md` (a «Refactor» column, a «Todos los refactors» row, a «Refactors» section, and the role in the deduplication key) count it apart from its scenario.
- **The refactor sees complexity, and may not raise it** (ADR-0013, F60). `python-uv`'s `complexity` control (L1, `measure`, `limit: 10`) runs `python_uv/lictor_complexity.py`, a module of the profile in `verification.files` that reads `src` with `ast` and imports, runs and configures nothing: `uv run python -I -B -m lictor_complexity src --out {out}`. - **Git runs hardened.** Every call in `GitCli` carries `core.fsmonitor=false` and `core.hooksPath=/dev/null`, ignores replaced objects and drops inherited locations (`GIT_DIR` and the like). `export_tree` and `capture` don't read user configuration either, so a global `core.autocrlf` can't change the tree under test. `export_tree` fetches through `refs/worktree/lictor/verified`, a ref of each worktree, so two runs in two worktrees of one repository never move the same one.
- **The control files include the common directory.** `GitCli` finds the repository by reading, never by asking git: `.git` is a directory, or in a linked worktree a file pointing to `<common>/worktrees/<name>`, whose `commondir` names the common directory. `_control_paths` takes `HEAD` and `config.worktree` from the worktree's directory and `config`, `hooks/` and `info/` from the common one, under the names they have in a normal checkout, plus the two pointers (the `.git` file and `commondir`). In a normal checkout the pointers don't exist, so its fingerprint is the one 0.2.0 computed. `restore` puts the pointers back first, one at a time, and reads every other path again after them, so a redirected `commondir` can't send the rest elsewhere.
- **A resume compares against the anchor.** The checkpoint records HEAD, the hash of `seal.json` and the fingerprint of the repository's control files (`observe_anchor`, set at `preflight`, after sealing and after each commit). `_integrity_refusal` (`cli.py`) compares the fingerprint first, reading bytes without running git, then the rest, and refuses with exit 10, also on uncommitted changes (D4). The anchor carries `format` (`ANCHOR_FORMAT`): one without it was written by 0.2.0, which didn't hash a linked worktree's common directory, and `anchor_from_older_version` refuses it before comparing, with its own message (start over with `--new`), not as tampering. What a crash can legitimately leave is accepted: the candidate of the last verification, the driver's tree before the seal, or, with `red_check` pending, one commit on top of the anchored head with its same tree (`baseline_head_accepted`): the repeated red check tests every green again. It raises the cost of a forgery, it doesn't rule one out: the checkpoint is within reach of the same user.
- **Checkpoints are written synchronously** (`DURABILITY`, `orchestration/graph.py`). With the default, a background thread writes the WAL while the agent runs: a kill loses it, and `IntegritySnapshot` reads it as tampering. Anything that invokes the graph must pass it. It doesn't cover `put_writes`, which LangGraph still leaves to a thread: `preflight` (it builds the verification environment), `build_driver`, `red_check`, `implement` and `verify` hold the saver's lock for the whole node (`_holding_checkpoint_writes`), so a write in progress ends before the snapshot and one not started waits. Still under that lock, once the node ends, the saver's connection is closed without folding the WAL and a new one opened (`_reconnected`): the old one kept descriptors to whatever a tampering left, unlinked `-wal` and `-shm` included, read the restored file through them and the run died with `no such table` instead of failing the attempt at `L0-estado` (F19). It stays open during the node on purpose: while it lives, a reader that may write can't be the last connection and fold the WAL when it closes. Python 3.13 shows the race and 3.12 hides it; `test_a_late_checkpoint_write_is_not_tampering` forces it on any version. A new node that runs agent or project code needs the same wrapper, and it can't touch the saver inside: the lock isn't reentrant, so the node would wait for itself forever. Only Lictor's own nodes run there, so that is a programming error for the suite to catch (the global `timeout` turns the hang into a failure with its traceback), not something production patches over. The wrapper relies on `SqliteSaver.lock`, so `langgraph-checkpoint-sqlite` is pinned below 4.
- **`lictor.json` holds what the person decides.** `lictor init` writes only `version`, `profile`, `backend.model` and `hints` (`_init_payload`); the rest comes from the profile on every load (`_merge_profile_defaults`), so a fix to the profile reaches a project without editing it. The file is validated first as `LictorFile` (what a person writes, which is also what the schema describes) and then resolved into `LictorConfig`. A key written replaces the profile's whole, except `controls`, which are `ControlChange`s by `id` (`_resolve_controls`): one with a profile `id` changes only the fields written (in `model_fields_set`, a written null included) and `enabled: false` drops it, with nothing else written beside it; another `id` adds a control, and goes after the change written before it, or at the end if it is the first. Which shape a change leaves is resolved before pydantic (`resolve_shape`, the table of ADR-0008, point 2), so each mistake has its own message: a control runs a command (`run`, and `level` and `report` to add one) or reads the run of another (`reads` and `adds`, `report: "coverage"`, and none of `empty_exit_codes`, `timeout_s` or `when_exists`); writing `run` over a reader makes it run, and writing `reads` and `adds` over one that runs makes it read. `run`, `reads` and `adds` may be left out but never null. Dropping an `id` the profile lacks is a typo and exits 10, naming the profile's ids. An empty list no longer means «no controls». The profile is `python-uv@0.2`: `@0.1` exits 10 with what changed, from the profile's `retired_versions`, so the full copies 0.2.0 wrote (`tests/fixtures/lictor_0_2_0.json`) no longer load.
- **L0 gates are not controls.** `L0-sin-cambios`, `L0-rutas`, `L0-sello`, `L0-supresiones`, `L0-entorno` and `L0-estado` are hardcoded in `VerifyAttempt`; `L0-sin-cambios` fails an attempt whose tree equals HEAD before anything runs. Levels L1–L5 are data: the profile's controls in `adapters/config/profiles/`, changed by `id` from `lictor.json` (see «`lictor.json` holds what the person decides»). A level says what a control is, not when it runs: that is `stage` (ADR-0007), written by `id` like `mode`. `attempt` (the default) runs in every verification of a run and in `check`; `check` never runs in a run, only in `lictor check`. `bootstrap` splits them with `controls_of_stage` (domain `stages.py`): `GraphContext.controls`, which `VerifyAttempt` gets, holds only the `attempt` ones, and `GraphContext.check_controls` the rest, only to name them. A run names them twice and never per attempt: `run.started` lists them in `check_controls` (`{id, level, mode, min_score}`), which `report.md` shows under «Controles solo en `lictor check`», before «Controles en medición» (a journal without the field lists none), and `_finish` adds one sentence to the reason when the run committed a green (`final_reason`, `committed_greens` against `green_at_load`): at the end of a run in a linked worktree it is fused with `integration_hint`, with the worktree's path, and a run that stops early there names that path too (`ResultBranch`), without inviting to integrate. A stop that resumes doesn't go through `_finish`, so it doesn't carry it. `stage` enters `config_fingerprint`, so changing it refuses a resume. If `check` fails after a run the scenarios stay green and the fix is the person's: nothing blames a scenario. No profile declares a `check` control; one that did would change what protects every project's run and goes in the CHANGELOG. `mode: measure` never blocks: result, exit code and output are recorded whether it passes or fails, in the `controls` of `verify.finished` and in `report.md`. A control with `report: "mutation"` or `report: "coverage"` also records its score (a `Score` derived from its report: `MutationScore` or `CoverageScore`, told apart by `kind` in the journal; a score without `kind` is no score, `score_from_record`). `coverage` reads the JSON coverage.py exports (`--cov-report=json:{out}`, `CoverageReader`) and computes the percentage from the counts, lines and branches together as coverage.py does (`coverage_score`); a run whose exit code is in `empty_exit_codes` and left no report, or one that measured nothing (0 statements and 0 branches), passes without a score, and with any other code fails. Percentages are shown cut to one decimal, never rounded up (`_percent_text`). For mutation: `scripts/mutation_score.py` deletes the previous export, runs the pass and its export and copies the counts to `{out}`, and leaves no report and exits non-zero if the export fails, so an old score can't pass for a new one. `mutation_score` counts as killed only what the tests killed, out of every mutant tried; timeouts, untested and suspicious ones count as not killed and are shown apart. `control_summaries`, `report.md` (under «Puntuaciones», whatever the mode) and `lictor check` show it beside the result. A mutation or coverage control may declare `min_score` (in `lictor.json`, a project decision, by `id` for the profile's): `enforce_min_score` (domain) fails it below that percentage, or with no score at all, in `check` and in a run. Lictor's own `coverage` is `block` with `min_score: 90` and `when_plugin: null`, so it can't inherit the profile's skip. Lictor's own is `block` at 95: under the worse platform (95,9 % on macOS; 96,3 % on Linux, where the six `hash_tree` mutants that need a non-UTF-8 name die) with room for known noise. The script also leaves `mutation-survivors.txt` beside `{out}`, which the CI keeps as an artifact. A report with no test cases passes only if its exit code is in the control's `empty_exit_codes` (the profile's `unit` declares `[5]`); `allow_empty` no longer exists and `lictor.json` with it is refused at load, naming what the profile declares. A control with `when_exists` is skipped only if that path is in neither HEAD nor the candidate (`control_path_status`), and fails if the attempt removed it; the skip and its reason go to `controls` and `report.md`. A control with `when_plugin` is skipped if the environment doesn't load that plugin (`missing_plugin`, against `VerificationEnvironment.installed_plugins`, always a tuple: the profile's `plugins` and what `plugins_command` found). It is only valid in a profile with a `plugins_command`: the `Profile` validator and `resolve_defences`, for the controls a project adds, refuse it otherwise. `python-uv`'s `coverage` (measure) needs `pytest_cov.plugin`, a dependency only a person can add, so a project without it sees the control skipped, not failed, in every run. `lictor check` does the same against HEAD and what it verifies.

  **A control may read the run of another** (ADR-0008). `ReaderControl` (`domain/controls.py`) has `reads` and `adds` instead of `run`, and nothing of a run of its own; `Control` is the union with `CommandControl`, and `CommandEntry` and `ReaderEntry` keep a `Read` off a command and an `Executed` off a reader. `python-uv`'s `coverage` reads `unit`, which then runs once: `effective_command` gives `unit` the reader's `adds` while the reader runs where it is verified (the `attempt` controls in a run, all of them in `check`, never what `--control` chose) and its plugin is loaded, composed by tokens with each `{out}` its own control's (`fill_report_paths`, which drops every report first). `verification_steps` decides the reader's plugin once for both turns, and both `VerifyAttempt` and `CheckProject` follow its steps through `take_turn`, `run_control` and `Readings`: the coverage report is read as soon as `unit` ends, under its conditions (not after a tampering, also after a timeout), and the reader only gives its verdict at its turn (`reader_outcome`, the table of ADR-0008, point 6), never reinterpreting `unit`'s exit code. A failed control that ran a command other than its `run` names it in the agent's error, with each `{out}` as configured and a sentence on what it is (`executed_as`, `failure_reason`); one skipped or unable to run names none. `doctor` warns of a reader only in `check` (`check_stage_ids`) and looks for no program of it. The rules of the pairing (`reader_problems`: an active JUnit control, before its reader, at most one reader, never an `attempt` reader of a `check` control) are validators of `LictorConfig` and `Profile`. The journal records a `Read` as `outcome: "read"` with `reads`, and `report.md` and `check` show it as «lee unit», marked «(de un unit fallido)» from the read control's result of the same verification. The project's `fail_under` doesn't apply (`--cov-fail-under=0`): a threshold is `min_score`. Lictor's own `coverage` writes its `run`, so it is a command control and `tests/unit` runs twice there.
- **`lictor check` verifies what `run` would, and what it leaves for later.** It runs the controls of both stages: what a run would, plus the `check` ones (ADR-0007), marked «(solo en check)» in its output so a failure after a run reads as what it is. One exception: with a reader in `check` and its read control in `attempt`, `check` never runs the `unit` without coverage the run ran, and marks its line «(con los argumentos de coverage, que solo corre en check)». `check_selection` (domain) completes a selection in one direction: a selected reader brings its read control, unless its plugin is missing, and `check` says so («Se ejecuta también unit, cuya ejecución lee coverage»); a selected read control brings nothing. There is no `--stage`: `--level` and `--control` choose across both. `CheckWorkingTree` verifies HEAD or, with uncommitted changes, the commit that committing them would make: `Vcs.capture` of the working tree (skipping `.lictor`) and `commit_tree` outside the branch, which only then needs an identity. Controls and acceptance run in a clean clone of it (`verification_tree`), in a throwaway environment built for that same commit, whose hash is compared at the end. There is no working-tree mode. It stops at the first blocking failure unless `--keep-going`; `--control` chooses by id, together with `--level`. Evidence goes to `.lictor/check/`, which each `check` replaces. It exits 0, 10 if a blocking control fails, 40 if the environment fails or changes. The CI's self-verification is `uv run lictor check --keep-going --level L1,L2,L4,L5`: every control but the acceptance, which is the `repro` cases, run by the `repro` jobs in parts. The `coverage` control runs everything else (`-m "not repro and not exhaustive"`) and fails on any failed test, so no test runs twice. Both leave out the `exhaustive` cells, which only `suite-completa.yml` runs.
- **A person can register what Lictor can't prove.** `lictor register <ID>...` (`RegisterScenarios`) takes the lock, refuses if a run can be resumed, needs a clean tree and an identity, is all or nothing (`registration_problems`), states what is asserted for a new or a reopened scenario and asks (or `--yes`; without a terminal it refuses). It makes one empty commit with a `Scenario:` per scenario and `Lictor-Asserted-By`, never `Lictor-Run`, and emits `scenario.asserted`. `SpecHistory` reads both trailers (`GreenRecord.by_lictor`, `asserted_by`); `spec.loaded` carries each green's commit, and `report.md` and `lictor status` show a green whose commit lacks `Lictor-Run` as registered by hand. Every green Lictor has committed carries `Lictor-Run` since its first version (`b4a603e`). The mark is informative: anyone can write a trailer. It is how a project that already has code adopts Lictor: register what the code meets before the first run, so the fresh driver is never told to make a working test fail.
- **Scenarios map to tests by what they executed, or by name.** With `link: "scenario"`, `map_test_cases_to_scenarios` takes the scenario from each case's properties; with `name`, it normalizes `IVA-001` to `iva_001` and looks for it in the test name or classname. Either way it requires exactly one test per scenario, or raises `DriverError`. `Scenario Outline` is refused at `load_spec`, so a scenario never has several cases.
- **Pausing is an interrupt.** On a rate limit, `pause` calls LangGraph `interrupt()` and `resume_to` records the node to return to. That attempt isn't counted. The CLI exits 50, and the next `lictor run` resumes from `.lictor/current_run` via `Command(resume=True)`. Exit codes are stable public API (`ExitCode` in `domain/errors.py`).
- **A backend that answers badly doesn't cost a scenario.** Status `auth`, or `AGENT_FAILURE_LIMIT` consecutive `error` calls, gives the signal `unavailable`: `pause` interrupts with the reason `agent_unavailable`, no attempt is spent and the CLI exits 40. It resumes the same way as a rate limit. An `error` below the limit doesn't spend an attempt either, for the driver too: `classify_agent` and `keeps_attempt` (domain) decide both, and `route_build_driver` sends a driver call that kept its attempt straight back to `build_driver`, with no red check judging its tree. `max_turns` spends one. A call that runs out of time spends one only if the model answered (`model_responded`: an `assistant` event whose model isn't `<synthetic>`); if it never did, it is an `error` («El modelo no respondió en N s»), so a hung backend pauses at the second call instead of quarantining scenarios, or `rate_limited` if the partial stream carries a `rejected` `rate_limit_event`. Either way the raw file keeps the partial stream.
- **Exit 40 means "couldn't run", not "the work failed".** `ENVIRONMENT_UNAVAILABLE` holds at start (`preflight`, `doctor`: no identity, a missing program, the temporary directory, `prepare`), on resume and mid-run: someone has to fix the environment and relaunch, and no scenario is to blame. Keep future environment failures, such as the sandbox, under this code and put the specifics in the message.
- **`forbidden_paths` and `banned_patterns` are heuristics of the profile.** The first are matched against each path component, ignoring case (on macOS `claude.md` opens as `CLAUDE.md`), and rejected in `L0-rutas`, along with any symlink. In the driver's own paths only what `driver_exempt_paths` names is allowed (`conftest.py`): the driver is sealed and committed, so a `tests/acceptance/CLAUDE.md` would plant as well as one in `src/`. Besides the Python configuration, `python-uv` lists what makes another tool run code or follow instructions from the tree it opens: `.claude`, `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `.mcp.json`, `.vscode` and `.github`. At the root they were already outside `paths.writable`; the entries cover them anywhere below. The second are case-insensitive regexes, in `L0-supresiones`. For the implementer and the refactor the suppressions of the added lines must fit in those of the removed ones, across the whole change, each counted by its exact text from where it matches to the line's end (`suppressions_not_moved`, `Vcs.removed_lines`; F72): moving a function with its `noqa` to another module, renaming, reindenting or joining equal ones passes, adding one or changing its text doesn't. The rule over added lines (`suppression_matches`) judges what a fresh driver adds (`CheckRed`, rejection `L0-supresiones`, before running anything): the driver is sealed and never judged again, so a `# noqa` or a `sys.path.insert(0, src)` it leaves stays for every attempt (F12). `python-uv` bans changing `sys.path` (insert, append, slice or reassign; reading it is fine): `src` goes behind the dependencies on purpose, and in front it can replace one. A sealed driver isn't checked. They are heuristics: they raise the cost of cheating, they don't close it. `sitecustomize.py` and `usercustomize.py` are listed as an extra defence; what keeps them from running is the startup path.
- **The agent runs without user or project settings.** `ClaudeCLI` passes `--setting-sources ""` and `--strict-mcp-config`, so hooks, permissions and `CLAUDE.md` from the machine or the repository don't apply. OAuth survives this. Automatic memory survives it too, so `--settings '{"autoMemoryEnabled": false}'` and `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` turn it off (`--bare` would, but it drops OAuth). `--tools` makes only the tool names of the allowed rules available (no web, subagents, schedules or messages), and `--permission-mode dontAsk` refuses whatever no rule allows: `acceptEdits` let `touch` through. The agent's environment is the caller's without `CLAUDE*` (but `CLAUDE_CONFIG_DIR`, where the session may live) and without `VIRTUAL_ENV`: launched from a Claude Code session or `uv run`, it inherited both. It reads `--output-format stream-json`, the only format with `rate_limit_event`. The first real pass (CLI 2.1.317) is `tests/fixtures/claude_stream_2_1_317.jsonl`.
- **The project keeps a stub of the skill; the content is the installed version's.** `lictor init` (unless `--no-skill`) and `lictor skill` write `.claude/skills/lictor/SKILL.md` from `skill/stub.md` (`application/skill.py`): a frontmatter with the description that triggers it and `` !`lictor skill --show 2>&1 || true` ``, which Claude Code runs before the model reads the skill, pre-approved by `allowed-tools`. Claude Code keeps only the first 5000 tokens of a skill when it compacts a conversation, so the profile's file splits at `<!-- lictor: detalle -->`: its essentials go where the body has `<!-- lictor: perfil -->`, after «Límites», and its detail after the body, and the content ends with `END_LINE`, which the header names so a cut skill is printed again. `doctor` warns (⚠, `skill=True` in `PreconditionsRequest`) only when the stub is there and isn't this version's; no stub is a decision. The agent never loads it (`--setting-sources ""`, and `Skill` isn't in `--tools`); `ClaudeCLI` compares `system/init.skills` with the copy's `.claude/skills/` and records any match in `AgentResult.project_skills`, which `agent.finished` carries and `RunProgress` shows with ⚠. Built-in skills can share a project's name, so a match tells, it doesn't reject.
- **Every wait for a process is bounded.** `SubprocessRunner` reads bytes and decodes them with `replace` (`e20`), gives the command `stdin=DEVNULL`, waits for it within its timeout, kills its whole group however it ends, and then gives the pipes `DRAIN_GRACE_S` (1 s): whatever still holds them escaped the group with `setsid`, and it stops being read, with a note in stderr (`d21`). That process stays alive; only the sandbox reaches it. Each stream keeps its first MiB and its last 15, cut on line breaks with the marker on a line of its own (a piece with no line break stays raw, so redrawn progress keeps its end), so `runs/` logs and raw streams are bounded per file, and their number by the retention of runs. `CommandOutput.timed_out` and `started` say what the return code can't. `ClaudeCLI` gets the same runner from `bootstrap` for the call, `health()` and `auth status`, and reads `cli_version` from the stream's `system/init`, not from a `health()` per attempt.
- **The prompt gets the scenario as its author wrote it.** `SpecSource.scenario_text` finds the scenario by its ID tag in the AST and takes its original lines, comments above it included, up to the next background, scenario or rule, after the backgrounds of the feature and of its rule. A doc string can't cut it (`d27`), and one that isn't found gives only its header.
- **Status comes from structured fields, never from the text.** `rate_limited` needs a failed call (`is_error` or a non-zero exit code) with `api_error_status` 429 or `rate_limit_info.status == "rejected"`, or that `rejected` with no `result` event at all. - **The terminal tells each step, from the journal.** `lictor run` wraps the project's journal in `ObservedEventLog` (`observed_journal`, `bootstrap.py`), and `RunProgress` (`domain/progress.py`) folds each event into a line on stderr once it is written: the call starting (`agent.started`, appended before the snapshot, with `max_attempts`), a failed verification, a green with its attempt, time and cost, collaterals on one line, quarantines, the seal and the totals. `--quiet` turns it off; stdout keeps only the outcome. `lictor status` folds the same journal for calls, cost and how each green came (implemented, collateral, registered again, from before), and takes the scenario and attempt in progress from the checkpoint; `describe_status` writes it, in Spanish, with the greens from before and the scenarios simply waiting on a line each, consecutive IDs as a range (`id_ranges`). - **A run's evidence lives in `.lictor/runs/<run_id>/<owner>/`**, where the owner is a scenario or `driver` (`application/run_files.py`). Each attempt leaves `NNN-implement.json` or `NNN-driver.json`, `.stderr.log` and the prompt it was given (`.prompt.md`, written before the call: the CLI gets it by argv, and its hash goes to `agent.finished` as `prompt`) beside it, and one directory per verification: `NNN-verify/` or `NNN-red/` with `acceptance.xml`, `acceptance.log`, `control_<id>.xml` (the report the control was given as `{out}`, whatever its format: a mutation control leaves JSON there), `control_<id>.log` and `error.txt`. A run that stops in `preflight` leaves `report.md` as it was. The same report counts the journal lines it skipped, corrupt or foreign; a forged line with the exact shape of an event can't be told apart.
- **What goes to the prompt is bounded; the rest goes to `runs/`.** `condense_error` keeps, in order, the reason, each failed case's name and message, and then details and assertion lines. Callers pass only the cases that matter, not expected pending reds. `render_full_error` has no limit and goes to `error.txt`.

Exit codes other than 0 stay normal while scenarios are pending, so the profile must declare which ones mean "tests failed". The run, the red, the impostors and `check` all use it; in `check` a trusted report then fails with any failed case.
- **Readers read facts; the domain gives every verdict** (ADR-0009). `ReportReader[R]` (`application/ports.py`) reads the path of `{out}` and returns `R | MissingReport | InvalidReport` (`domain/reports.py`); it never raises because of what the file holds. `ReportReaders` gives one typed reader per format with a report (`junit`, `coverage`, `mutation`); `exit-code` has no report and no reader. Nothing at the path is missing; a directory, a broken link, an unreadable or empty file, bytes that don't decode (JUnit follows XML's rules: BOM and declared encoding; JSON must be strict UTF-8) or impossible counts are invalid. The report only ever comes from `{out}`, never from the stdout or from a path written in the file. Each verdict is a pure function of `domain/verdicts.py` over the fact, the `Execution` (exit code, timeout, whether it was cut) and `empty_exit_codes`; a command cut by its timeout fails first, saying so. `tests/unit/characterization_reports.jsonl` is their contract, measured against master before ADR-0009: a row only changes with a deliberate change, in the commit that makes it.
- **A result is a variant, and the journal keeps a projection of it** (`domain/results.py`). A control ends `Skipped`, `NotExecuted` (its `when_exists` was removed) or `Executed`, which is `Judged` (its report and verdict; cases and score derive from the report) or `Unjudged` (it tampered with the state: no report read, no verdict). The acceptance is no control: `AcceptanceRun`, `Unjudged`, `Crashed` or `Reported`. `consequence` decides what a verification does with a result (go on, fail there, or end at `L0-estado` whatever the mode, so a `measure` control can't let a tampering pass) and `failure_of` what the agent reads, with the output added when only it explains the failure. `run_control` (`application/control_reports.py`) runs, logs, reads and judges a control for both `VerifyAttempt` and `CheckProject`. The journal writes `lictor.verify.finished.v2` through one codec: `controls.<id>` with `outcome`, `mode` and only that variant's fields (case counts, never the cases), and `acceptance` apart, or `null`. There is no `control_durations`: durations are summed from what ran. A `v1` event is from an earlier version: `report.md` counts it and doesn't read it; a record that doesn't follow the schema is left out. Every log starts with the command that ran (`save_output`).
- **The agent's commands aren't the controls.** `agent_commands` in the profile are runnable as they stand and include acceptance, and each must match `agent_tools`. Controls keep `{out}` and belong to verification. A control may add `agent_run`, the command with which the agent measures it by itself (F55): `agent_measures` (domain `controls.py`) tells the implementer each minimum (`min_score`) of the controls the run verifies whose plugin the environment loads, with that command, and the command joins those Bash allows (`{medidas}` in `implement.md`). Verification never runs it. `agent_run_problems` decides what `agent_tools` allows: a profile with one it doesn't allow fails to load, as does a `lictor.json` that writes one (`_reject_unrunnable_agent_runs`), while one inherited from the profile under narrower tools is dropped by `domain_controls`, untold. `python-uv`'s `coverage` declares one; a project that changes `adds` changes it too.

## Constraints Enforced by Tests

These are easy to trip:

- **No profile tool names in `src/lictor` outside `adapters/config/profiles/`.** `test_no_profile_tool_names_outside_profiles_dir` fails on any standalone `ruff`, `mypy`, `pytest`, `pytest-bdd` or `uv` in source, including docstrings, comments and prompt templates. Toolchain specifics belong in profiles.
- **The profile's modules are written for Python 3.9.** They run in the project's interpreter. `test_profile_modules_python39.py` parses each `python_uv/lictor_*.py` with 3.9's grammar, requires `from __future__ import annotations` where annotations would be evaluated, and refuses `isinstance(x, A | B)`; where `uv python find 3.9` finds one without downloading, it also imports each module there. Before 0.17.0 three of them failed to import on 3.9.
- **The domain can't import I/O modules** (`subprocess`, `sqlite3`, `shutil`, `os`, `socket`). `test_domain_has_no_io_imports` checks this separately from `.importlinter`.
- **`schema/lictor.schema.json` must equal `LictorFile.model_json_schema()`**, the file a person writes, not the resolved `LictorConfig`. After changing `adapters/config/models.py`, regenerate it with `export_config_schema` (`adapters/config/loader.py`).
- **Mutation testing covers the domain and the small application modules** listed in `[tool.mutmut]` (`anchor`, `events`, `seal`, `spec_history`, `agent_events`, `commit_green`, `commit_refactor`, `quarantine`), with the test files listed there. Tests for new domain modules must be added to that list to count. The four large use cases stay out: their decisions live in the domain (`classify_agent`, `keeps_attempt`, `path_within`, the routing), and manual mutants cover their wiring against the whole suite.

## Testing Without an LLM

Set `backend.kind` to `"fake"` in `lictor.json` to use `FakeExecutor` (`adapters/agents/fake.py`). Its modes are `good`, `fail`, `cheat`, `conflict`, `rate_limit` and `crash`, and they can be set per scenario. A refactor call has its own `refactor_mode` and writes only what `files_to_write` holds under `refactor` or `refactor:<ID>`: by default nothing, so it ends `unchanged`. `bootstrap_runtime` reads its options from `.lictor/fake_executor.json`, or accepts `executor=` directly. `tests/integration/test_e2e_demo_iva.py` runs full cycles against a copy of `examples/demo-iva/`, inside a linked worktree with `fake_executor.json` in its `.lictor/`: from the person's checkout the run would get a worktree of its own, without it.

For behaviour the modes can't express, pass `FakeExecutor(effect=fn)`: `fn(task, scenario_id, attempt)` runs arbitrary code in the agent's turn (forged bytecode, git commands, killing the run) and may return a status. `effect` can't go in `fake_executor.json`, so it needs `executor=`.

## Running in Parallel

The suite runs under `pytest-xdist` (`-n auto`), which is not in `addopts` because `mutmut` runs pytest without it. Each worker builds its own `template` under its own `tmp_path_factory` base, every case works in its `tmp_path`, and no test opens a port; `test_each_worker_builds_its_own_template` holds the first. The only thing workers share is the `uv` cache, which locks itself.

Every test has a `timeout` of 600 s (`pytest-timeout`, method `signal`, in `[tool.pytest.ini_options]`): the slowest case takes 84 s locally with coverage and CI runners are up to about 2.6 times slower, so 300 s left too little margin. A test that hangs fails with its traceback instead of stalling the suite. Keep the slowest case well below it. `mutmut` isn't affected: it kills its mutants by CPU time, far sooner. Memory is bounded by `scripts/mutation_score.py`: at most 4 mutants at once (`--max-children`) and 1 GiB of data per process (`RLIMIT_DATA`, which Linux enforces), so a mutant that loops piling up memory gets a `MemoryError` and counts as killed. One that turned `os.scandir(entry.path)` into `os.scandir(None)` in `hash_tree` reached 13,8 GB without it, and hung the self-verification in CI.

No test judges a wait by the wall clock: a loaded machine made `< 4 s` fail twice (F22, F39). A test of a call that must not wait for a process leaves that process alive for `DETACHED_LIFE_S` (300 s, `Detached` and the `detached` fixture in `tests/conftest.py`) and checks it is still alive when the call returns; one of a timeout gives the command that long and checks the mark it would leave at its end isn't there. Either fails only if the call really waited, and the fixture kills what is left.

The CI runs in layers (`.github/workflows/`). In a pull request, `-m "not repro"` runs on Linux with Python 3.12, 3.13 and 3.14 and on macOS with 3.14 (3.12 on macOS is what a maintainer runs locally). `repro` runs on Linux with 3.13 and on macOS with 3.14, each in three parts split by `pytest-split` from `.test_durations`: three keep a Linux part under a macOS one, which sets the critical path. The self-verification measures coverage without `repro`. A last job (`Presupuesto`, `scripts/ci_budget.py`) compares each job and the critical path with the budget, the queue apart, and warns without failing. `suite-completa.yml` runs everything, `exhaustive` included, on the six platforms: every night (off the hour, which GitHub delays least), by hand, and before a release, which `release.yml` only publishes if it passes. It runs with `--dist worksteal` (see «What to run and when»), and its own `Presupuesto` (`ci_budget.py full-suite-jobs`) compares each job with its 60 min, without the critical path of a pull request, and never stops the release that waits on it. Its Linux 3.12 cell measures the whole coverage, `repro` included, in its summary; its Linux 3.13 cell leaves the artifact `test_durations`, the duration of every `repro` case without coverage. Copy it over `.test_durations` when the repro cases change much; a case missing there counts as the average, so a new one is never lost, only worse placed. `exhaustive` marks the cells of a matrix beyond one per class, which a PR doesn't run. A nightly can fail without a failed test when GitHub finds no macOS runner («not acquired by runner»): rerun it with `gh run rerun --failed <id>`, which before a release also reruns the publishing job that waited on it.

`tests/conftest.py` gives every test its own `TMPDIR` and a `LICTOR_HOME` beside it, so no test writes the real `~/.lictor`: Lictor refuses a home under the temporary directory, and every directory pytest hands out is under the system's. It also clears the variables of a verification that may be running the suite, test by test: left in place, a nested `uv sync` would rewrite the verification environment and a nested pytest would load its plugins. It can't happen at startup, because xdist workers inherit them. A test that launches an interpreter with an exact environment needs `-B`, or its bytecode lands in that environment and fails the hash.

## Audit Reproduction Cases

`tests/integration/repro/` holds the cases from the v0.1 audit, one file per correction phase. Unlike the other e2e tests, they use the real `python-uv` profile and `uv`, with the configuration from `lictor init`, so they are the model for new end-to-end tests. Add `-m "not repro"` to skip them while iterating.

- **A case runs on a light project unless it says otherwise.** `make_project` drops the profile's `lint`, `types`, `unit` and `coverage` by `id` (`light_config`, `LIGHT_DISABLED` in the harness; a case that names `unit` or `coverage` keeps both, `LIGHT_PAIRS`, because a reader without its read control exits 10), the way a person would in `lictor.json`, and rewrites the template's only commit, so the history has the same shape. The acceptance, the L0 gates and every control a case adds still run. Those dropped controls were most of what a case cost (`mypy` from a cold cache and `pytest` on every verification) and decided nothing about a defence the acceptance proves.
- **A case runs without the refactor unless it says otherwise** (ADR-0010). `make_project` writes `"refactor": {"enabled": false}` (`without_refactor`), unless the case is `@smoke` or `@with_refactor`, or its `config_changes` decide the refactor; the harness `Agent` has a `refactor` callable (`no_refactor` by default, `good_refactor` changes the code and keeps what it does). `false_greens` also checks the final tree when it isn't a `Scenario:` commit, which after a refactor it isn't. The kill matrix turns it on for the `refactor:*`, `verify_refactor:*` and `commit_refactor:*` points (mode `refactor`) and checks one refactor commit per green.
- **`@smoke` keeps the whole configuration of `lictor init`.** It marks a group of 5 to 10 cases that prove everything fits: a whole cycle to green, from the person's checkout too, a control that blocks, a coverage score and its minimum, `check` by level and by id, and `doctor`.
- **`@all_controls` keeps it for a case whose defence is about a dropped control.** Mark a case with it when the dropped control is what the case attacks, measures or needs to produce its output. Without the control the case would pass because nothing happened: `tools == {"pytest"}` holds when `mypy` never ran. Examples are a permissive user configuration of `ruff` or `mypy`, an evasion of L1 or L2, the output of a unit test, or what runs during lint and types. A case that asserts a dropped control fails visibly without the mark; the risk is a case that asserts an absence. In doubt, mark it.
- **`tests/integration/test_repro_layers.py` lists the three groups** (`with_refactor` too). It fails if a case loses its mark, and it runs in every gate, not only where the cases do.

- A case asserts the desired behaviour and stays under `@pending(phase, finding)`, a strict `xfail` that only tolerates `AssertionError`. Closing a case means removing its marker. Every phase of the plan is closed, so no case is `@pending`; the two limits only the sandbox of increment 4 closes are `@known_limitation`, also a strict `xfail`.
- A case that fixes behaviour that already holds, as `test_phase7_spec_edit.py` (an uncommitted edit of a `.feature` stops the run with 10 and survives), needs no marker: it guards against a regression.
- Preconditions go through `require`, which raises `ReproSetupError`, so a broken set-up fails the test instead of counting as the expected failure.
- `false_greens` re-checks every `Scenario:` commit in a clean clone with an oracle that uses neither pytest nor the project venv. Keep it that way: cases `c3`, `c4` and `c6` fool anything that runs inside the suite.
- An attack that needs `.git` or `.lictor/` comes in two variants: one from `task.cwd`, which must prove the agent really was in a copy (`_require_copy`), and one by absolute path against the project, which must prove the anchor catches it. Without the first the case passes because the attack didn't run; without the second it proves nothing about the anchor.
- The harness `DRIVER` is a `pytest-bdd` driver whose steps read their values from the Gherkin; edit its checks through `TOTAL_CHECK` and `NEGATIVE_CHECK`. An attack that only touches ignored files or paths outside the copy needs `no_op_change`, or the attempt stops at `L0-sin-cambios` before reaching the gate the case is about.
- `test_phase4_recovery.py` kills a real process with SIGKILL at every node, before, during and after its work, plus `worktree:durante`, with the worktree created and nothing started in it, and `red_check:registro`, after a registration moved the branch. `kill_runner.py` is that process. It runs from the person's checkout, as `lictor run` does, and the matrix resumes from there through the index; `LICTOR_KILL_IN_PLACE` runs in the project itself instead, and `LICTOR_KILL_BRANCH` gives `--branch`. Each point belongs to one class in `KILL_CLASSES`, by recovery mechanism (what the kill leaves and what the resume must do with it); the first point of each class runs in a PR and the rest are `exhaustive`. A new point needs a class, and a new mechanism a class of its own: `test_every_point_has_a_class_and_every_class_a_cell_in_the_pr` fails otherwise. The cells run Lictor in a process of their own, which coverage doesn't measure, so leaving the exhaustive ones out of the `coverage` control costs no coverage.
- `run_lictor` (harness) runs in the project itself, as inside a linked worktree: the same code, with the git directory in one place instead of two, which `test_v0_3_0_worktree.py` covers. `run_from_checkout` runs as `lictor run` from a person's checkout, and `run_worktree` finds a run's worktree in the index. The cases of the worktree Lictor creates are in `test_v0_3_0_own_worktree.py`, two runs in parallel with a commit by hand included. Set `LICTOR_KILL_MATRIX` to a path to collect the result of each cell.

`tests/integration/test_example_prestamos.py` keeps `examples/prestamos-biblioteca` honest: its features load, and the three scenarios its code already meets pass, with an oracle that reads the Gherkin and calls the code without pytest-bdd.

The audit report, the original lab scripts and the phase tracking live in `.audits/analisis-base/`, which is git-ignored and exists only on the maintainer's machine.

## Code Style & Conventions

- **Python Version:** 3.12 idioms throughout (`X | Y` union types, built-in collections `list[T]`, `dict[K, V]`).
- **Typing:** Strict typing mandatory (`py.typed` is packaged). Every function, method parameter, and return value must have explicit type annotations.
- **Line Length:** 100 characters maximum (configured in Ruff).
- **Suppressions:** Avoid `# noqa`, `# type: ignore`, or `# pragma: no cover`. If an external library has missing stubs, use targeted overrides in `pyproject.toml` rather than inline ignores.
- **Domain Errors:** Raise domain-specific exceptions from `lictor.domain.errors` rather than generic `ValueError` or `RuntimeError`.
- **Event-Driven Auditability:** Significant domain actions must emit typed `Event` objects adhering to CloudEvents specification.
- **Language:** User-facing strings, error messages, event data, commit subjects and ADRs are in Spanish; identifiers and docstrings are mostly in English. Commits use Conventional Commits with Spanish descriptions. Design documents are in `references/` and `docs/adr/`.

## Agent Dos and Don'ts

### Do
- Run `uv run ruff check .`, `uv run mypy --strict src scripts`, and `uv run python scripts/check_architecture.py` before completing any change.
- Implement new capabilities starting from the Domain and Ports, then implement Use Cases, and finally attach Adapters.
- Provide comprehensive unit tests in `tests/unit/` for all new domain and application logic.
- Mock or fake external processes (`subprocess`, `git`, external CLI binaries) using corresponding ports in unit tests.

### Don't
- **Never** import `pydantic` or any third-party framework into `src/lictor/domain/`.
- **Never** create cross-dependencies between adapter packages (e.g., `adapters.agents` importing `adapters.vcs`).
- **Never** perform direct git operations (commit, push, checkout) inside agent tasks unless specifically implementing the `Vcs` port.
- **Never** lower coverage thresholds in `pyproject.toml` or `lictor.json` to make tests pass.
