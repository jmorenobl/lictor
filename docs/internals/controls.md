# Controls, reports and verdicts

How controls run, are read and judged, what the agent is told to run, and what a run says it proved. Part of the reference linked from [AGENTS.md](../../AGENTS.md#how-a-run-works); each point names the code, ADR and finding behind it.

- **L0 gates are not controls.** `L0-sin-cambios`, `L0-rutas`, `L0-alcance` (only a refactor's), `L0-sello`, `L0-supresiones`, `L0-entorno` and `L0-estado` are hardcoded in `VerifyAttempt`; `L0-sin-cambios` fails an attempt whose tree equals HEAD before anything runs. Levels L1–L5 are data: the profile's controls in `adapters/config/profiles/`, changed by `id` from `lictor.json` (see «`lictor.json` holds what the person decides»). A level says what a control is, not when it runs: that is `stage` (ADR-0007), written by `id` like `mode`. `attempt` (the default) runs in every verification of a run and in `check`; `check` never runs in a run, only in `lictor check`. `bootstrap` splits them with `controls_of_stage` (domain `stages.py`): `GraphContext.controls`, which `VerifyAttempt` gets, holds only the `attempt` ones, and `GraphContext.check_controls` the rest, only to name them. A run names them twice and never per attempt: `run.started` lists them in `check_controls` (`{id, level, mode, min_score}`), which `report.md` shows under «Controles solo en `lictor check`», before «Controles en medición» (a journal without the field lists none), and `_finish` adds one sentence to the reason when the run committed a green (`final_reason`, `committed_greens` against `green_at_load`): at the end of a run in a linked worktree it is fused with `integration_hint`, with the worktree's path, and a run that stops early there names that path too (`ResultBranch`), without inviting to integrate. A stop that resumes doesn't go through `_finish`, so it doesn't carry it. `stage` enters `config_fingerprint`, so changing it refuses a resume. If `check` fails after a run the scenarios stay green and the fix is the person's: nothing blames a scenario. No profile declares a `check` control; one that did would change what protects every project's run and goes in the CHANGELOG. `mode: measure` never blocks: result, exit code and output are recorded whether it passes or fails, in the `controls` of `verify.finished` and in `report.md`. A control with `report: "mutation"` or `report: "coverage"` also records its score (a `Score` derived from its report: `MutationScore` or `CoverageScore`, told apart by `kind` in the journal; a score without `kind` is no score, `score_from_record`). `coverage` reads the JSON coverage.py exports (`--cov-report=json:{out}`, `CoverageReader`) and computes the percentage from the counts, lines and branches together as coverage.py does (`coverage_score`); a run whose exit code is in `empty_exit_codes` and left no report, or one that measured nothing (0 statements and 0 branches), passes without a score, and with any other code fails. Percentages are shown cut to one decimal, never rounded up (`_percent_text`). For mutation: `scripts/mutation_score.py` deletes the previous export, runs the pass and its export and copies the counts to `{out}`, and leaves no report and exits non-zero if the export fails, so an old score can't pass for a new one. `mutation_score` counts as killed only what the tests killed, out of every mutant tried; timeouts, untested and suspicious ones count as not killed and are shown apart. `control_summaries`, `report.md` (under «Puntuaciones», whatever the mode) and `lictor check` show it beside the result. A mutation or coverage control may declare `min_score` (in `lictor.json`, a project decision, by `id` for the profile's): `enforce_min_score` (domain) fails it below that percentage, or with no score at all, in `check` and in a run. Lictor's own `coverage` is `block` with `min_score: 90` and `when_plugin: null`, so it can't inherit the profile's skip. Lictor's own is `block` at 95: under the worse platform (95,9 % on macOS; 96,3 % on Linux, where the six `hash_tree` mutants that need a non-UTF-8 name die) with room for known noise. The script also leaves `mutation-survivors.txt` beside `{out}`, which the CI keeps as an artifact. A report with no test cases passes only if its exit code is in the control's `empty_exit_codes` (the profile's `unit` declares `[5]`); `allow_empty` no longer exists and `lictor.json` with it is refused at load, naming what the profile declares. A control with `when_exists` is skipped only if that path is in neither HEAD nor the candidate (`control_path_status`), and fails if the attempt removed it; the skip and its reason go to `controls` and `report.md`. A control with `when_plugin` is skipped if the environment doesn't load that plugin (`missing_plugin`, against `VerificationEnvironment.installed_plugins`, always a tuple: the profile's `plugins` and what `plugins_command` found). It is only valid in a profile with a `plugins_command`: the `Profile` validator and `resolve_defences`, for the controls a project adds, refuse it otherwise. `python-uv`'s `coverage` (measure) needs `pytest_cov.plugin`, a dependency only a person can add, so a project without it sees the control skipped, not failed, in every run. `lictor check` does the same against HEAD and what it verifies.

  **A control may read the run of another** (ADR-0008). `ReaderControl` (`domain/controls.py`) has `reads` and `adds` instead of `run`, and nothing of a run of its own; `Control` is the union with `CommandControl`, and `CommandEntry` and `ReaderEntry` keep a `Read` off a command and an `Executed` off a reader. `python-uv`'s `coverage` reads `unit`, which then runs once: `effective_command` gives `unit` the reader's `adds` while the reader runs where it is verified (the `attempt` controls in a run, all of them in `check`, never what `--control` chose) and its plugin is loaded, composed by tokens with each `{out}` its own control's (`fill_report_paths`, which drops every report first). `verification_steps` decides the reader's plugin once for both turns, and both `VerifyAttempt` and `CheckProject` follow its steps through `take_turn`, `run_control` and `Readings`: the coverage report is read as soon as `unit` ends, under its conditions (not after a tampering, also after a timeout), and the reader only gives its verdict at its turn (`reader_outcome`, the table of ADR-0008, point 6), never reinterpreting `unit`'s exit code. A failed control that ran a command other than its `run` names it in the agent's error, with each `{out}` as configured and a sentence on what it is (`executed_as`, `failure_reason`); one skipped or unable to run names none. `doctor` warns of a reader only in `check` (`check_stage_ids`) and looks for no program of it. The rules of the pairing (`reader_problems`: an active JUnit control, before its reader, at most one reader, never an `attempt` reader of a `check` control) are validators of `LictorConfig` and `Profile`. The journal records a `Read` as `outcome: "read"` with `reads`, and `report.md` and `check` show it as «lee unit», marked «(de un unit fallido)» from the read control's result of the same verification. The project's `fail_under` doesn't apply (`--cov-fail-under=0`): a threshold is `min_score`. Lictor's own `coverage` writes its `run`, so it is a command control and `tests/unit` runs twice there.
- **`lictor check` verifies what `run` would, and what it leaves for later.** It runs the controls of both stages: what a run would, plus the `check` ones (ADR-0007), marked «(solo en check)» in its output so a failure after a run reads as what it is. One exception: with a reader in `check` and its read control in `attempt`, `check` never runs the `unit` without coverage the run ran, and marks its line «(con los argumentos de coverage, que solo corre en check)». `check_selection` (domain) completes a selection in one direction: a selected reader brings its read control, unless its plugin is missing, and `check` says so («Se ejecuta también unit, cuya ejecución lee coverage»); a selected read control brings nothing. There is no `--stage`: `--level` and `--control` choose across both. `CheckWorkingTree` verifies HEAD or, with uncommitted changes, the commit that committing them would make: `Vcs.capture` of the working tree (skipping `.lictor`) and `commit_tree` outside the branch, which only then needs an identity. Controls and acceptance run in a clean clone of it (`verification_tree`), in a throwaway environment built for that same commit, whose hash is compared at the end. There is no working-tree mode. It stops at the first blocking failure unless `--keep-going`; `--control` chooses by id, together with `--level`. Evidence goes to `.lictor/check/`, which each `check` replaces. Under each failed control, blocking or measuring, it prints why (`CheckProjectResult.failures`, `ControlFailure.condensed`: a reason Lictor already bounds as a list whole, JUnit failures condensed to `FAILURE_CHARS`) and where all of it is (`.lictor/check/<id>.error.txt`, `render_full_error`), and no longer repeats the first failure at the end (H1 of 0.20.0). With a base (`--base` or `api.base`) it adds «Cambios que ningún control ejecutó» from that base to what it verified, with this same `check`'s JUnit (`UnexecutedSurvey`). It exits 0, 10 if a blocking control fails, 40 if the environment fails or changes. The CI's self-verification is `uv run lictor check --keep-going --level L1,L2,L4` and, in a job of its own at the same time, `--level L5` (the mutation): together, every control but the acceptance, which is the `repro` cases, run by the `repro` jobs in parts. The `coverage` control runs everything else (`-m "not repro and not exhaustive"`) and fails on any failed test, so no test runs twice. Both leave out the `exhaustive` cells, which only `suite-completa.yml` runs.
- **A suite that crashed proves nothing.** The report is deleted before each run. `trust` (`domain/verdicts.py`) is the only thing that makes a `Reported`, a report that can be trusted; anything else is `Crashed` with its reason: a suite cut by its timeout, one that left no report or an invalid one, one without test cases, one with an exit code outside `acceptance.failure_exit_codes`, or one with a failure code and no failed test. Exit codes other than 0 stay normal while scenarios are pending, so the profile must declare which ones mean "tests failed". The run, the red, the impostors and `check` all use it; in `check` a trusted report then fails with any failed case.
- **Readers read facts; the domain gives every verdict** (ADR-0009). `ReportReader[R]` (`application/ports.py`) reads the path of `{out}` and returns `R | MissingReport | InvalidReport` (`domain/reports.py`); it never raises because of what the file holds. `ReportReaders` gives one typed reader per format with a report (`junit`, `coverage`, `mutation`); `exit-code` has no report and no reader. Nothing at the path is missing; a directory, a broken link, an unreadable or empty file, bytes that don't decode (JUnit follows XML's rules: BOM and declared encoding; JSON must be strict UTF-8) or impossible counts are invalid. The report only ever comes from `{out}`, never from the stdout or from a path written in the file. Each verdict is a pure function of `domain/verdicts.py` over the fact, the `Execution` (exit code, timeout, whether it was cut) and `empty_exit_codes`; a command cut by its timeout fails first, saying so. `tests/unit/characterization_reports.jsonl` is their contract, measured against master before ADR-0009: a row only changes with a deliberate change, in the commit that makes it.
- **A result is a variant, and the journal keeps a projection of it** (`domain/results.py`). A control ends `Skipped`, `NotExecuted` (its `when_exists` was removed) or `Executed`, which is `Judged` (its report and verdict; cases and score derive from the report) or `Unjudged` (it tampered with the state: no report read, no verdict). The acceptance is no control: `AcceptanceRun`, `Unjudged`, `Crashed` or `Reported`. `consequence` decides what a verification does with a result (go on, fail there, or end at `L0-estado` whatever the mode, so a `measure` control can't let a tampering pass) and `failure_of` what the agent reads, with the output added when only it explains the failure. `run_control` (`application/control_reports.py`) runs, logs, reads and judges a control for both `VerifyAttempt` and `CheckProject`. The journal writes `lictor.verify.finished.v2` through one codec: `controls.<id>` with `outcome`, `mode` and only that variant's fields (case counts, never the cases), and `acceptance` apart, or `null`. There is no `control_durations`: durations are summed from what ran. A `v1` event is from an earlier version: `report.md` counts it and doesn't read it; a record that doesn't follow the schema is left out. Every log starts with the command that ran (`save_output`).
- **The agent's commands come from the controls** (F83, ADR-0018). There is no list of them: `agent_commands` is gone, and a `lictor.json` with it exits 10 (`agent_commands_message`), after the profile it names is known, so a retired profile still says so first. `agent_commands` (domain `controls.py`), called once in the graph (`_agent_commands`), gives `fixes` and `checks` from the `attempt` controls and the acceptance: what counts is a control that blocks every attempt and whose plugin the environment loads (`counts_for_agent`). Each gives its `agent_fix` (the command that leaves done what it checks; `python-uv`'s `format`: `uv run ruff format src`), and its check: its `agent_run`, or its `run` without the report (`without_report`: the token with `{out}` goes, and the option before it when the token is `{out}` alone; a positional `{out}` gives none; a `run` without `{out}` stays as written). A control with a fix gives its check too, so a fix that doesn't fix what the control reads shows before the verification. A read control is checked with its `run`, never with its reader's `adds`; a reader gives its `agent_run` or nothing. The acceptance goes last. Only what `agent_tools` allows stays (`allowed_by`, prefix of `Bash(<p>:*)` or the exact command, judged with `{lictor_files}` unsubstituted), each once. The implementer and the refactor get `checks` as `check_commands` and `fixes` apart: `{comprobaciones}` lists the checks one per line, `{arreglos}` asks to run the fixes after the last change and before the checks (`fixes_text`), and `{bash_admite}` says what Bash accepts, by the tools' prefixes, not by these commands (`agent_command_lines`); the driver gets them all in its list and no line asking for the fixes. A command naming `{lictor_files}` makes the call copy the profile's files (`_profile_files`). With `format` off, in `measure` or in `check`, nothing asks to format, so its fix never rewrites files nobody verified (F84's `L0-alcance`); Lictor never formats the agent's tree (F75). `agent_run` also says how the agent measures a control by itself (F55): `agent_measures` tells the implementer each minimum (`min_score`) of the controls the run verifies whose plugin the environment loads, with that command (`{medidas}`). Verification never runs either. `agent_run_problems` (over `allowed_by`) decides what `agent_tools` allows for `agent_run` and `agent_fix`: a profile with one it doesn't allow fails to load, as does a `lictor.json` that writes one (`_reject_unrunnable_agent_runs`), while one inherited under narrower tools is dropped by `domain_controls`, untold. **A changed run can't inherit the agent's command** (`_reject_stale_agent_commands`): when the project writes a control's `run` (a reader's `adds` or `reads`, or the `run` of the control it reads) and the profile gives it an `agent_run` or `agent_fix` the project didn't write, the load exits 10 (`stale_agent_command_message`): write it, or `null`. `agent_fix` is a field of a run (`RUN_FIELDS`): turning a control into a reader drops it, and a reader that writes it is refused. A project that doesn't use `format` writes `{"id": "format", "enabled": false}`.
- **The public API is compared with the commit the run started from, or where it left `api.base`** (ADR-0017, F80). `python-uv`'s `api` control (L1, `measure`, `report: "api"`) runs `python_uv/lictor_api.py`, a stdlib module of the profile in `verification.files` (`ast`, valid back to Python 3.9, importing and running nothing of the project): `uv run python -I -B -m lictor_api src --out {out}`. Its definition is Lictor's, fixed by `test_lictor_api.py`: a name is public when it can be reached from a public module (no part starting with `_`): its static `__all__`, or else what it defines without `_`, what it takes with `import *` and, in a package's `__init__.py`, what it imports from its own subpackages. Each export is followed to its definition, private modules included; what `if TYPE_CHECKING:` imports doesn't count. It counts functions, classes, methods, properties, static and class methods, constants, class attributes, fields and `Enum` members, inherited from project classes too, and of each callable every parameter with its kind and default, and `async`; a class's signature is its `__init__` or the one a dataclass, `NamedTuple` or pydantic model builds. The report is facts (`ApiReport`, `ApiReader`). There is one base: `preflight` keeps a SHA in the state (`api_base`) and nothing else, HEAD's or, with `lictor.json`'s `api.base` (a reference, `"origin/main"`, validated by `reference_name_problem`, refused at load without an active control with `report: "api"`, and in `config_fingerprint`), where HEAD left it (`resolve_base`: `Vcs.resolve_commit`, then `Vcs.merge_base`; amendment 0.20.0, H4), so every run of a work is compared with the branch it goes to, not with its own start; a reference that names no commit, or shares no ancestor here (a shallow clone), is ✗ `config` with its own message (`missing_base`, `no_common_base`); `ApiBaseline` (`application/api_baseline.py`) runs the same command in a clean clone of it, inside `IntegritySnapshot`, once per run (in memory by SHA), never read from `runs/`. `all_breaks` (domain `api.py`) gives what a base name no longer does: `removed`, `kind`, `async`, and in a call a parameter removed, renamed, moved, losing a way of being passed or its default, a new one without default, a `*args`/`**kwargs` gone; moving a definition and re-exporting it, or moving a method up to a base, breaks nothing. `api.accepted` in `lictor.json` (in `config_fingerprint`) accepts a break by its name, an alias or what holds it. `api_verdict` fails naming what is broken and not accepted (without a base it only gives facts); the verdict's reason gives only facts (`broken_reason`; `named=None` for the whole list, which `check` leaves in `api.error.txt`): in either mode `{medidas}` carries `IMPLEMENTER_API`, and in `block` also `IMPLEMENTER_API_BLOCKS` (declare `LICTOR: SPEC_CONFLICT` if the scenario can't be met without the break), while `api.accepted` is told only to the person (`API_ACCEPT_HINT`, in `check`). `RunProgress` prints ⚠ after a green that broke something new: neither broken at the start (`run.started` keeps `api_start`, `api_start_record`, from «La API frente a su base») nor by an earlier green of the run. `Measure.breaks` keeps the set of breaks, and `refactor_regressions` discards at `L0-regresión` a refactor that adds any to its green's set, in either mode (`REFACTOR_API`). `verify.finished` keeps `api: {symbols, base, broken, accepted, problem}` (`RecordedApi`); `report.md` has «API pública» with what the last passing verification left broken and, per name, the files of HEAD citing it outside `paths.writable` (`TextSearch.cited_in`, a whole-word fixed-string `git grep`); `lictor check` gives the number of public names, and compares with `api.base` or, replacing it, `--base <rev>`, both from where what it verified left them; without an API control `--base` still decides «Cambios que ningún control ejecutó» and `check` says the API isn't compared (`api_uncompared`); a base that doesn't resolve stops it before anything is built. The driver's changes count against the same base: in `block`, a break of the sealed driver fails every attempt until the person accepts it. It sees signatures, not behaviour.
- **A run says what its greens can be trusted for** (ADR-0020, `domain/proof_level.py`). `proof_level` reads the resolved defences (`ProofDefences`, built once by `bootstrap.proof_defences` from `Defences` and the `attempt` controls): **resultado probado** with the profile's whole oracle (`impostors` judged by rule C, `stub_rule_c`, with `red_kinds`, `link: "scenario"`, `interface_impostor`), **resultado leído** with a stubs' impostor and less than that (rule C alone, or the driver's own constants, `declared_stubs`, ADR-0021, amendment of 0.24.0), **básico** without one, saying less, never more; the driver's constants never give «resultado probado», whatever else is there. The gaps Lictor knows how to compute go apart, each a stable code with its sentence (`Gap`: `rojo_sin_clase`, `enlace_por_nombre`, `ya_cumplido_sin_prueba`, `valor_sin_peso`, `entorno_sin_hash`, `sin_supresiones`, `sin_controles`, `sin_lectura_de_controles`, `control_sin_plugin` from `installed_plugins`, `plugins_sin_comprobar` without the environment). `doctor` and a new run say it in «Nivel de prueba», after «Los controles pasan en HEAD» (⚠ with gaps, ✓ without; never an exit code), and «Órdenes del agente» warns of a blocking control or the acceptance the agent's tools don't let it run (`unrunnable_by_agent`, D10). `run.started` keeps `proof: {level, gaps}` in codes (`proof_record`), and `RunProgress`, `status` (`status_line`, `--json`'s `proof`) and `report.md` («Nivel de prueba» in «Resumen» and «Lo que este nivel no comprueba» right after) read it; no commit carries it. Without a plugin what used to mislead is said or kept quiet: the red of «Medidas del driver» is the JUnit status (`RedMeasure.status`) without `red_kinds`, «Tests aceptados sin comprobar» says a basic profile checks none, «Cambios que ningún control ejecutó» says why it can't know without a survey (`UNREAD_BY_PROFILE`), the refactor only hears fewer tests discard it when a control counts them (`guards_tests`), each rule of the three prompts that names a list has its own sentence without one (`domain/prompt_lists.py`: suppressions, forbidden paths, greens, what the driver doesn't touch), and a report whose cases map to no scenario brings the acceptance's output, or, with the driver sealed, says the tests were cut short (`mapping_failure_reason`). The driver's prompt asks every profile for stubs that fail with the language's «not implemented» and never return a value, recovered in each test where that would stop the whole process (a Go `panic`), and for a test of an error that checks which; without `interface_impostor` it says an already met scenario is registered by a person (`already_met_line`).
- **The check of each control that blocks every attempt is granted to the agent as is** (ADR-0018 amended, S17 of 0.25.0). `granted_tools` (`domain/controls.py`) adds an exact `Bash(<check>)` rule for each counting control and for the acceptance, unless a rule already allows it; `bash_admits` names those apart («y estas órdenes tal cual»), and the `agent_run` of a granted control needs no rule of its own (`granted_check`, `_asked_and_not_granted` in `loader.py`). A control with `"agent": false` (`grants_agent`) gets none and `doctor` doesn't warn of it; a command with `*`, `?` or `[` gets none either, since a rule reads them as wildcards, and `doctor` says why. Lictor's own `lictor.json` sets `"agent": false` on `secrets` and `coverage-domain`, which can't pass in the agent's copy (no `.git`, no `.coverage` of the control before): a new control that depends on `.git` or on another control's output needs it too.
- **A minimum of coverage with nothing measured waits for the first green** (S18 of 0.25.0). `nothing_to_measure` (`domain/results.py`) holds when a coverage report measured nothing and its command ended in time with 0 or one of `empty_exit_codes`; `CheckProject` downgrades that failure to a measure only with `CheckProjectRequest.unstarted`, which `doctor` (HEAD) and `check` set from `project_unstarted`: scenarios in `features/`, no `Scenario:` commit, the whole history. In an attempt it always fails. `check` also waits for the acceptance before the first run with the same fact (`acceptance_pending`): no file under `paths.driver` but those `driver_exempt_paths` exempts, and says «sin driver todavía»; a project without scenarios, like Lictor itself, always runs its acceptance.
