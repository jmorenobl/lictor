# Preconditions and the start contract

What `doctor` and a new run check before anything is spent, and what a run tells at its end. Part of the reference linked from [AGENTS.md](../../AGENTS.md#how-a-run-works); each point names the code, ADR and finding behind it.

- **Prerequisites are checked before anything is spent.** `CheckPreconditions` (`application/usecases/preconditions.py`) is what `preflight`, `doctor` and a resume check: a clean tree (not on resume, which checks it its own way; in the person's checkout only a warning for `doctor`), the committer identity as `commit_tree` will see it (`Vcs.committer_identity`, `git var GIT_COMMITTER_IDENT` through the same `_run_git`, with git's message), the executor, the private temporary directory, the first word of every control and of acceptance (on the `PATH` the command gets, `VerificationEnvironment.search_path`, or committed and executable in HEAD if it is a relative path) and the verification environment. `preflight` and a resume (`_check_resume_guard`) look only for the programs of the `attempt` controls, so a `gitleaks` that only the CI has doesn't stop a run that leaves it to `check`; `doctor` asks with `check_stage=True`, so it looks for all of them, though a missing program of a `check` control is a warning in «Comandos de verificación» (`CHECK_STAGE_ONLY`) and an empty command still fails, and warns (⚠, «Momento de los controles», `check_controls_warning`) whenever a control is `check`, without changing its exit code; with a `lictor.json` that doesn't load there are no controls to name. The domain decides the exit code (`precondition_exit_code`): 10 if anything is the project's (configuration, an empty command, a dirty tree), 40 if only the machine has to change. `preflight` builds the run's environment after the cheap checks and before `load_spec`, holding the checkpoint lock like any node that runs code it didn't write, so a broken `prepare` or no identity stops before any agent call (`e29`). `doctor` also checks the features (`features=True`) with the rule `load_spec` uses: `spec_problems` (`domain/spec_rules.py`) gets what `GherkinSource` read of each file and lists every problem with file, line and what to do (a file that doesn't parse, an outline, a scenario without exactly one valid ID, a duplicate ID, an ID on a feature or rule, or no scenario at all); `load` raises them all in one `SpecError`. An empty file, or a feature without scenarios, demands nothing: it isn't `blocking`, `doctor` shows it with ⚠ without changing its exit code and the run skips it. `doctor` reports every check without stopping, a `lictor.json` that doesn't load included: it is `✗ Configuración` (`config_problem`) and `unconfigured_preconditions` (`bootstrap.py`) checks what needs neither an executor nor an environment, leaving the executor, the commands and the environment «no comprobado» (F30). It builds its own environment, never a run's: `VerificationEnvironment.kept` in `.lictor/doctor-env/` (`DOCTOR_ENV_DIR`, outside `.lictor/doctor/`, which each `doctor` replaces), kept from one `doctor` to the next (G5): with `prepare`, `ensure` rebuilds it when its key changes (`env_key`, the configuration's hash and HEAD's tree, `_doctor_env_key`; every `ensure` of one `doctor` uses it, `_env_id`; without commits there is no key); without one, what its commands left there (Go's caches) stays. What `doctor` says decides no green, and a new run checks the controls on HEAD again in its own environment, so this shares no cache that decides a verification. «Entorno de verificación» says it was reused (`KEPT`), `doctor --fresh` removes it first (`remove_tree`), and `retire` removes it from the worktree too, before `git worktree remove`. `check` keeps a throwaway one (`VerificationEnvironment.throwaway`, under the temporary directory).
- **`doctor` and a new run check the start contract** (ADR-0015, F66, F67, F70). Two checks after «Entorno de verificación», on the environment just built (inside `doctor`'s throwaway `with`, which deletes it on exit), only when `PreconditionsRequest.survey_dir` is given: `doctor` gives `.lictor/doctor/survey`, `preflight` `runs/<id>/start` (a resume doesn't run `preflight`). **«Dependencias de la verificación»** is ✗ `config` (exit 10, no new code): the profile's `acceptance.needs_plugins` (plugin → how to add it, `python-uv`: `pytest_bdd.plugin`) against `installed_plugins` (`missing_plugins`), and each program a command launches through `uv run` that the environment doesn't have, or that only the machine has (`uv run pytest` without pytest in the lock ran `/usr/bin/pytest` and exited 0), as the survey reports it (`program_problems`; a `check` control only warns). **«Lo que los controles no ven»** only warns. Its facts come from the profile's `survey` command (`python_uv/lictor_survey.py`, in `verification.files`, stdlib only and valid back to 3.9, importing and running nothing of the project), run by `StartSurvey` (`application/start_survey.py`) in a clean clone of HEAD without `IntegritySnapshot`, with `{in}` (a JSON of every command control of both stages and the acceptance, by `id`, and the profile's `detect`) and `{out}`; `SurveyReader` and `survey_report` (`domain/survey.py`) read it, apart from the controls' `report`. The module knows pytest and `uv`: what each command runs or reads, or `unknown` with why (`make`, `tox`, `sh -c`, `--pyargs`, an unknown option followed by a value, a configuration it can't read), pytest's configuration as pytest finds it (`pytest.ini` first, `[tool.pytest]` and `[tool.pytest.ini_options]`, `tox.ini`, `setup.cfg`; `testpaths`, `python_files`, `addopts`), the files of tests (named as such, outside `src`, defining a test), the `conftest.py` each command loads and the repository modules its tests import (followed), the other files that import the project and the commands whose paths contain them; a subdirectory with a `detect` file is another project, named and skipped. `blind_spots` (`domain/blind_spots.py`) judges with `L0-rutas`'s rules (`StartRules`: `writable` minus `forbidden_paths`, the driver always out, `check_only`): `sin_control`, `solo_check`, `sin_cambiar` (run by the run, out of the agent's reach), `cargado` (loaded by the run, imports the code, out of reach: F67, with the names imported) and `sin_lector`; an `unknown` command silences what it might see, and without modules in `src` the check is «no comprobado». A survey that fails only warns. The person's decisions go in `lictor.json` `blind_spots.accepted` (paths, outside `config_fingerprint`): those files are only counted. A profile field in `lictor.json` (`survey`, `acceptance.needs_plugins`) exits 10 with its own message. `run.started` keeps `blind_spots` (`blind_spots_record`), `RunProgress` prints its lines with ⚠ and `report.md` has «Lo que los controles no ven».
- **The controls that block pass on HEAD before the first attempt** (amendment 0.19.0 of ADR-0015). After «Lo que los controles no ven», with the same `survey_dir`, `CheckPreconditions._head_controls` runs once, in the environment just built and on a clean clone of HEAD, the `attempt` controls in `block` (`head_controls`, through `CheckProject` with `control_ids`, so a reader brings its read control), inside `IntegritySnapshot` and with `ensure` afterwards. Each that fails is ✗ `config` «Los controles pasan en HEAD» (`domain/head_controls.py`), with its condensed error (`CheckProjectResult.blocked`, `FAILURE_CHARS`) and where its output is (`<survey_dir>/controles/`); a changed environment is `environment`. It is what the first attempt would pay for and the agent can't fix: a configuration the profile overrides, a warning made an error, an unformatted base. The acceptance doesn't run: before the driver there is nothing to judge. With no blocking control it is skipped («ningún control bloquea»). A control whose program «Comandos de verificación» can't find, and a reader of one, isn't run there (`blocking_on_head`, a ⚠ naming them): it would fail again and make the machine's 40 the project's 10; with none left the check is «no comprobado» (`NONE_STARTS`). A repro case whose control attacks during verification arms it from the agent's turn, or the start of the run catches it first. On Lictor itself it costs about 112 s of `doctor`'s 115 (`unit` and `coverage`): one more verification of the dozens a run makes, which spares an attempt on what the agent can't fix; it stays as it is (H6 of 0.20.0). With `api.base`, `api` isn't run there: **«La API frente a su base»** (`API_BASE`, `_api_against_base`) measures HEAD and the base once, guarded by `IntegritySnapshot`, and a break of HEAD nobody accepted is ✗ `config` with `api` in `block` (`head_api_broken`: accept it in `api.accepted` or change the mode) and a warning in `measure`; a base that can't be measured, the same by mode. `PreconditionsReport.api_start` carries the comparison to `run.started`.
- **A run tells what it changed that no control executed** (amendment 0.20.0 of ADR-0015, H2, `domain/unexecuted.py`). In `_finish`, before `run.finished`, when HEAD differs from `started_at` (the state's HEAD of `preflight`, never `api_base`), `UnexecutedSurvey` (`application/unexecuted.py`) runs the start's survey on the final HEAD (`StartSurvey.execute(rev=)`) and `unexecuted_changes` crosses the diff with `blind_spots` of that tree: `sin_control`, `solo_check`, `sin_lector` (`cargado` and `sin_cambiar` run, out of the agent's reach, and don't count), plus a test file a command names whose JUnit in the last passing verification (`verified_step`: `control_<id>.xml`, `acceptance.xml`) has no case of it, by `classname` (`sin_ejecutar`: `-m "not integration"` over a file all marked), Python outside `code_dir` nothing reads (`sin_leer`) and what isn't Python (`no_es_codigo`). The features and the driver run in the acceptance; `code_dir` isn't listed (a linter reads it all, `CODE_NOTE`); deleted files go apart and accepted ones are counted; with a command nobody understands no test is judged. Facts only, and a failure reading them (git failing) is its `problem`, never the end of the run: `lictor.run.unexecuted.v1` `{started_at, head, files, deleted, accepted, notes, problem}` and «Cambios que ningún control ejecutó» in `report.md`, after «API pública»; a run that didn't end says so there.
- **The start contract reads the CI, and `--cov` as pytest-cov does** (amendment 0.19.0 of ADR-0015, F76, F78). `lictor_survey.py` reads `--cov` as an option with an optional value over `addopts` and the command together, `addopts` first: `--cov=X` doesn't change what is collected, and a `--cov` at the end of `addopts` eats the command's first path (`eaten`). `configuration_problems` (`domain/blind_spots.py`) turns that, and a `--cov` in `addopts` with a minimum (`gate`: `--cov-fail-under` or coverage.py's `fail_under`), into ✗ `config` in «Dependencias de la verificación»: with that minimum the acceptance exits 1 with no failed test. An `unknown` command says how many test files it leaves unjudged. The CI is read by Lictor, not the survey: `YamlCiReader` (`adapters/ci/yaml_ci.py`, PyYAML's `SafeLoader` through `yaml.compose` for the lines, `CiReader` in `ports.py`) takes from HEAD each command of each step's `run:` in `.github/workflows/*.yml|yaml` (split into commands outside quotes; `continue-on-error` demands nothing) and each hook of `.pre-commit-config.yaml` (`entry` + `args` if `local`, or the command the profile gives its `id` in `survey.ci_hooks`, with `pass_filenames`, `files`, `exclude` and `stages`). `StartSurvey` passes them in `{in}` as `ci`, and the survey recognises them with the controls' rules: `tool` (tool and subcommand; `ruff format` without `--check` only counts in a hook) and `covers` (the Python files it reaches), for each control too, which is so recognised by its command, not its `id`. `blind_spots` warns (⚠) of `ci_sin_control` and `ci_mas_ficheros` with `file:line`, and «Tests que ningún control ejecuta» names the CI steps that do run them. `blind_spots.accepted` takes «file: command» (`ci_entry_matches`); a path alone doesn't accept a step. Only `pytest`, `ruff check`, `ruff format` and `mypy` are compared.
