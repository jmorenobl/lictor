# The oracle: driver, red check and proofs

How the driver's tests become a trustworthy oracle: the red, the impostors, collaterals and registration. Part of the reference linked from [AGENTS.md](../../AGENTS.md#how-a-run-works); each point names the code, ADR and finding behind it.

- **Git is the source of truth for green scenarios, and for what they were green for.** `SpecHistory` (`application/spec_history.py`) takes, for each scenario, the most recent commit whose `Scenario:` trailer names it, and hashes that scenario in the features of that commit's own tree (`GherkinSource.spec_hashes`, cached by commit and file). `classify_scenarios` compares it with the current hash: `green`, `reopened` if it differs or isn't found, `new` without a commit. The hash (`spec_hash`) covers steps with their kind, doc strings, tables, backgrounds and examples, not names, tags, comments, spacing or the keywords' language; the form is Lictor's own, so a new `gherkin-official` reopens nothing. There's no hash trailer and nothing to migrate. `load_spec` classifies before `build_driver`, so the driver's prompt lists the greens and asks to update the reopened ones (`scenario.reopened`); `CheckRed` classifies again from git, not from the checkpoint. Changing commit messages or trailers can break resume.
- **The red is judged by class** (`judge_red`). A green must pass. A pending one, reopened or new, must fail with a valid red, and what happens when it passes depends on the driver. With the sealed driver its test was proved when it was sealed: a reopened one is registered again without the agent (as when the scenario wasn't found in its green commit's tree: a change to `features/` breaks the seal) and a new one is a collateral green. With a fresh driver nothing tells a pass from a vacuous test. A new one is `unproven`, and the impostor of the interface tries to prove it (ADR-0011, `_prove_or_reject`); see «A new scenario the code already meets is proved, not assumed» below. Proved ones are registered after the seal, in the same `advance_head`; any other rejects the driver as `sin_prueba`, retryable when the agent can fix the test (`InterfaceProof.fixable`: it never called the interface, it passed with an altered result, or it failed but not by its own assertion), and final at once, exit 10, when no retry changes what the impostor can tell (nothing it returned could be altered, a run told nothing); when attempts run out the stop says first to fix the test and then, if the code already met the scenario, to register it with `lictor register <ids>`. A profile without `interface_impostor` keeps the old rule: retryable, with a message that claims nothing. A reopened one is `respecified`: the step may still hold the old value, so the run stops with exit 10 without retrying (`especificacion_cambiada`), and a person who knows the change was only wording registers it with `lictor register`; the impostor never runs for it. So nothing is registered inside `red_check` before the seal, and only what the impostor proved after it. What passes without the agent goes into one empty commit on top of HEAD (`Scenario:` for each, `Lictor-Collateral` for collaterals; its subject names one scenario or counts several, `registration_subject`), with `scenario.reregistered` or a collateral `scenario.green`. Every `scenario.green` names the commit whose `Scenario:` trailer names it: after `VerifyAttempt`, the implemented scenario's is the parent of the collateral one the branch moves to.
- **The profile declares what makes the oracle valid** (`oracle`, only in the profile, read by `resolve_defences`). `link: "scenario"` maps each test to the scenario it executed, as the plugin `lictor_outcome` reports it in JUnit properties (`lictor.scenario`, `lictor.feature`); a name that contradicts it, or carries an ID without executing it, rejects the driver, and so does executing it from any file but the scenario's own (`Scenario.file`, passed to `map_test_cases_to_scenarios` as `files` by `CheckRed` and `VerifyAttempt`): pytest-bdd reads a copy with the same tag even if it isn't a `.feature`, which `load_spec` never loads. `red_kinds` lists the failures that count as red: `lictor.failure` is `assertion`, `not_implemented` or `error`, decided by the exception's class in the plugin, never by its text, and `not_implemented` also needs `lictor.origin` in `paths.writable` outside `paths.driver` (`red_failure_problem`). `interface_impostor` proves a new scenario that already passes with a fresh driver (see below). `impostors` reruns the acceptance of a fresh driver in clones where each matching line becomes each replacement, `{code, name, double}`: in `python-uv`, `return None`, `return True` and the two doubles of `python_uv/lictor_doubles.py` (`ONE` and `EMPTY`, see «The stubs' impostors ask for an assertion of a Then» below). Evidence goes to `NNN-red/impostor-<n>/`. A fresh driver with tests of no scenario is rejected (`sin_escenario`). Without `oracle` the old rules apply: any failure is red and tests map by name. The plugin runs in the process under test, which can forge it as it can forge the report (`c6`).
- **A new scenario the code already meets is proved, not assumed** (ADR-0011, F58, `domain/interface_proof.py`). The profile's `oracle.interface_impostor` names a variable (`LICTOR_IMPOSTOR`, which `reserved` covers through `LICTOR_*` and the `Profile` validator checks), a control mode and the modes (`mas`, `menos`). `CheckRed._prove_interface` runs the acceptance once per mode, each in a clean clone of the candidate and inside `IntegritySnapshot`, passing the variable through `VerificationEnvironment.run(extra_env=)` as JSON with the mode, the absolute `writable` and `driver` roots of that clone, the stubs it must leave unwrapped (`stubs`, file → lines, empty here) and the steps to alter (`steps`, the domain's `ALTERED_STEPS`: `when` and `then`; the plugin has no default and fails to load without it); evidence goes to `NNN-red/interfaz-<modo>/`. The plugin `python_uv/lictor_impostor.py` (in `verification.files` and `plugins`, idle without its variable) installs a `sys.meta_path` finder when it loads, so it wraps each module of `writable` outside the driver as it is executed: a driver that did `from paquete import f` would keep the original if it wrapped later. It wraps functions, coroutine functions and non-dunder methods, static and class methods and property getters, never classes or generators (a coroutine's caller is the frame that creates it, not the loop; it counts once awaited, from the step it was created in, and its result is altered when the `await` ends; before 3.12 only `asyncio.iscoroutinefunction` still sees the wrapper as one); an altered value the driver hands back to the interface goes back real, if it is immutable and not one Python shares (a list the driver changed is its own), and so does a frozen object of value, each altered field of one, and a mutable one whose fields are still the objects the impostor gave (`snapshots`): one the driver changed is its own; what reaches the interface for the driver through a library is counted and never altered: `lictor.interface.via` when the project calls it after the driver entered it through a library (typer keeps the command it decorates before the impostor wraps it), `lictor.interface.handed` when the library calls what the driver handed it, both by step, and `lictor.interface.entry.<step>` names the first library from the driver outside the standard library (what Python generates for a project module, as a dataclass's `__init__`, is the project's, and a coroutine the project created walks from its creator, not the loop; ADR-0011, amendment of coroutines and libraries); a call whose caller's file is in the driver runs the real function and, but in the control and only when made from a step `steps` names, alters its result (B: what a Given, a fixture or code outside a step gets stays real; a fixture counts as outside even when a When requests it, because pytest-bdd resolves a step's fixtures inside the step, so `pytest_fixture_setup` marks it) (`alter`: number ±1, a `date` or `datetime` ±1 day (ADR-0012), `bool` negated, text or collection one element longer or shorter (a text in `menos` loses its last character and, if that was blank, its last that isn't, F85), `None` for a sentinel (`AlteredByLictor`, which also fills an empty collection), an object of value (a dataclass, a `NamedTuple`, a pydantic v2 model, an attrs class: every field at once, up to 4 levels, in a copy of its class built with `copy.copy` and `object.__setattr__`, never its `__init__` or validators; a member of an `Enum` that isn't a `Flag`: the next in `mas`, the one before in `menos`), anything else (a service, a combined `Flag`) left alone and not counted; an exception swallowed in `mas`, replaced by `ImpostorError` in `menos`. A list or tuple changes at its start with an element of its own form, so a test of its first element or of each element's attribute fails by its assertion: `mas` puts the last one in front, altered if its kind is known, and `menos` drops the first; a dict in `mas` gains a key with such a value. Its tests table, `_CHECKS` in `test_lictor_impostor.py`, fixes what each way of checking a list proves; `[-1]` is a known limit, and the first of a list of one is proved by its statement when the Gherkin weighs it). It reports `lictor.interface.calls` and `lictor.interface.altered` per test, and the same by step (`.given`, `.when`, `.then`, from `pytest_bdd_before_step`; outside a step only the total counts them), and `lictor.interface.altered_none`, the altered results that were None (an order's). `lictor_outcome` adds `lictor.step`, the kind of step that raised the test's failure (kept in `pytest_bdd_step_error` and written in `makereport` only for that same exception, so an `xfail` in a step counts nothing), `lictor.frame` (the file of the last frame inside the project, the test's own when pytest raises for it; only an absolute path counts, so the relative one a compiled module names its source by, `src/lxml/parser.pxi`, is of no place, for `lictor.origin` too), `lictor.line` (that frame's line), `lictor.statement` (F85: the statements the failure was raised in, one per frame from the step function's, found by its code from `step_func`, unwrapped first, while each frame is in the project, `file:line:fed`; `line` is the first of the innermost statement of the module holding the frame's line, and `fed` the lines of its function that load a simple name it binds, followed transitively, a compound statement by its head only, an `assert` by its test, never its message; it stops at the first frame outside the project, and is empty if a frame of the project has no source or shares its line with another statement, `a; b` or `if x: assert y`, since a shorter chain joins more easily; the hook never raises) and the kind `impostor`, by the exception's class. `interface_proof` (domain) proves a scenario only if its test passed in the control having called the interface from a When or a Then and, in every mode, had a result altered and failed by an assertion of a Then whose frame is in `paths.driver`, or by the impostor's error in a When or a Then (ADR-0011, amendment B); a run that crashed or didn't map proves none, and so does a mode that altered what a Given or a fixture got. The outcomes: `no_llama` (no call, only from a Given: detail `dado`, or only through a library that called what the test handed it: detail `entrega`, with `libraries`), `sobrevive`, `no_aserta`, `fuera_del_entonces` (an assertion of the driver in a Given, a When or outside a step, its message in the detail), all four retryable, and `sin_alterar` (nothing altered from the When on, or only an order's None, with the test passing), `a_traves` (from the When on it only reached the interface through a library that entered the project: the person reads which, `through_note`; in the stubs it is rejected as `sin_codigo`) and `no_concluyente`, final (and `ilegible`, see below). The impostor numbers the driver's calls in each test and reports which raised unaltered (`lictor.interface.raised_at`) and which had their exception swallowed or replaced, with the step (`.swallowed_at`, `3:then`): a `probado`, `no_aserta` or `sobrevive` with one the control never raised is `provocada`, final (`provoked_in`): an altered value went back to the interface, a small integer Python shares, and made it raise. **The scenario's value weighs the verdict** (ADR-0016, `domain/gherkin_proof.py`): with the profile's `interface_impostor.gherkin` (`LICTOR_GHERKIN`), the control also tells `python_uv/lictor_gherkin.py` to number the values each Then receives from the Gherkin (its parser's, converted, plus `datatable` and `docstring`; `lictor.gherkin.*`) and to say which its bytecode never loads (any opname with `LOAD_FAST`, `LOAD_DEREF` or `LOAD_CLOSURE`: 3.13 joins two in one), and the interface traces each driver call (`trace`: step, function, a hash per argument, `lictor.interface.trace`). `weighed_proof` decides, in order: a value a Then receives and never reads is `ignora_el_valor`, retryable, over any proof, telling the step and the value; `provocada`; `probado`; a `no_aserta` whose every objecting mode failed with an `error` in a Then with statements in the driver (`InterfaceProof.broke_at`, `driver_statements`) is `probado` (detail `misma_lectura`) when every value is read and each broken chain joins one of the read assertions (`GherkinFacts.read_at`, `reads_what_broke`: one is a prefix of the other, or where they part the broken statement feeds the reading one: `root = parse(r.xml)` above `assert root.findtext(…) == v`), and `ilegible`, final, when the Gherkin weighed nothing (`_weighed_by_statements`, amendment of ADR-0016 in 0.21.0, F85; `unreadable_result_note` for the person); and a test the interface left `sobrevive`, `no_aserta`, `sin_alterar` or `a_traves` (`weighs_the_gherkin`; never `fuera_del_entonces`, whose fix is moving the assertion) is run again over those tests only (`targets`, which the plugin deselects by their marks), a second control and each alterable value changed alone per mode (`_weigh_the_gherkin`, evidence `NNN-red/gherkin-control-bis/` and `gherkin-<mode>-<n>/`, `stubs-` before them over the stubs): a value is read when a Then's assertion of the driver fails in both modes, an input when the trace's calls change in an argument two controls agree on (`reached_the_interface`), and if every value that isn't an input is read, at least one, and the When or the Then reached the interface, it is `solo_el_valor`, final: the agent hears only not to change it, and the person reads facts and where (`only_the_value_note`), with `_READ_THEM_HINT` instead of an invitation to `lictor register`, since a test comparing the value with what a Given stored looks the same. A value the parser extracts and the function doesn't take is only counted (`unreceived`): a regex's alternative is a right test. The message of `sin_alterar` only tells the agent not to change that test, since it reads it when another scenario is retried; why the impostor couldn't judge it (`unalterable_note`) goes only where no agent reads it, the final rejection or the last attempt. `no_aserta` names the exception, the step, the file and line and the mode, and says the other value is Lictor's and the test mustn't handle it apart: with the file alone, the agent moved its steps out of it. A test that ignores the result, or checks it weakly (`assert x`, `is not None`, `isinstance`, `!=`, `pytest.raises(Exception)`, two calls compared), survives. All of them must be proved or nothing is registered: once sealed, the next red would register an unproved one as a collateral. The proved ones go in one empty commit on top of the driver's (`Lictor-Collateral: <driver>`, `Lictor-Proof: interfaz`, subject «ya se cumplía»), with `scenario.green` carrying `collateral: true` and `proof: "interface"`, and `driver.sealed` lists them in `already_met`; `RunProgress` (`already_met`), `status` and `report.md` («Ya se cumplían», «verde (ya se cumplía)») count them apart. It proves the test reads the result, not that it compares it with the scenario's value: a driver that copies what the code returns into the assert passes it (`@known_limitation`, until a semantic judge of the driver, phase 2c of the roadmap). **What the red check saw, and what C would say, is measured** (`domain/driver_measures.py`): `CheckRed` writes `lictor.driver.measured.v1` once per red check of a fresh driver, after its impostors and before `driver.sealed` or `driver.rejected`, so a rejected driver is measured too. It names its step (`step`) without hashing it, because the rejection still writes `error.txt` there; the dedup of `report.md` keys it by that path. It holds, per scenario, how each pending test failed at the red (`red_measures`), how it fared with each stub constant, named by `impostor_name`, and what C would say (`rule_c`: a Then's assertion of the driver, not applied), and what the interface proved (`outcome`) with its counts by step, the step each mode failed in and what reached it through a library in the control (`via`, `handed`, `libraries`; a column of «Medidas del driver»), what the interface alone said when the Gherkin weighed it (`interface`), the modes with a provoked exception (`provoked`) and what the Gherkin's impostor saw (`gherkin`: `values`, `unread`, `unreceived`, `read`, `inputs`, `survived`, `errors`, `place`, `read_at`; a «Gherkin» column). `report.md` shows them in «Medidas del driver»; no verdict, prompt or message reads them. How long it took is recorded too (F52): `CheckRed` times each run of the acceptance in `_run_acceptance_suite` and gives it a phase by its evidence directory (`red_check_phase`: the step's own is `red`, `impostor-<n>` is `stubs`, `interfaz-*` is `interface`, `gherkin-*` is `gherkin`), and `driver.measured`, `driver.sealed`, `driver.rejected` and `driver.checked` carry `duration_ms` and `phases` (`red_check_timing`: runs and milliseconds per phase). `RunProgress` adds it to the seal's or rejection's line (`red_timing_text`), and `report.md` adds «rojo» to the total duration and lists each in «Comprobaciones del rojo». The stubs' impostors count their stubs first: with none they don't run, and `driver.sealed` says `stub_impostors: 0` instead of passing them; a new test that fails by `NotImplementedError` with no stub to replace is refused as `impostor`.
- **The stubs' impostors ask for an assertion of a Then** (ADR-0012, F64, `domain/stub_proof.py`). Each constant runs the whole acceptance in a clean clone with every stub replaced (`CheckRed._run_stub_impostors`); a run that crashes or doesn't map counts for no test, one that kept a stub rejects the driver (`impostor_problem`: write it on one line), and if every run told nothing the driver is rejected. `stub_proof` judges each new pending test by what each constant reported (`caught`): if it passes with every plain constant, or with the first one (the no-op, `return None`), it goes to the impostor of the interface; otherwise it is accepted only if some constant made an assertion of the driver fail in a Then; else it is rejected as `fuera_del_entonces`, `sobrevive` or `no_aserta`, with the step, the line and the constant (a double's failure named first), all retryable. The doubles are what let a right test reach its assertion: `ONE` (true, one element, yes to every order) and `EMPTY` (false, empty, no to every order) answer an attribute, an index, a call or an arithmetic operation with a child of their kind (one per name and key), equal nothing but themselves, give `nan` to `float()`, an unlikely number to `int()` and their repr to a format, copy and pickle as themselves, have no special names, and end: deeper than `DEPTH` or past `BUDGET` operations in a test (the module is also a plugin, only to reset that count per test) they raise `LictorDoubleExhaustedError`. Without them C rejected 9 of 347 right tests of the passes; with them, none. Every constant but the first goes through `lictor_doubles.stub(name)`, which gives None when called from an `__init__`, the only value Python lets it return: with `True` or a double there the object couldn't be built in a Given or a When, no test reached its Then and the driver was rejected whatever its tests (F68, `test_v0_14_1_init_stub.py`). What goes to the interface runs `_prove_interface` with `_ToProve(stubs_at=<first constant>)`: each clone has its stubs at `return None`, evidence in `NNN-red/stubs-interfaz-<mode>/`, and the plugin is told their lines (`stubs`) and leaves those functions unwrapped, since what a stub returns is Lictor's constant (with them wrapped, `r in (None, True)` was proved). `stub_verdict`: `probado` accepts; `sin_alterar` (it called code that already exists, nothing alterable) and `ilegible` (its Then couldn't read the altered result, with no value to weigh) accept unchecked, in `driver.sealed` as `stub_unchecked` and in `report.md` («Tests aceptados sin comprobar», `unchecked_note`), never told to the agent; anything else rejects with the interface's message headed «pasa aunque los stubs no estén implementados» (`stub_reason`), but `no_llama`, which there means nothing it checks comes from code that already exists, has its own (`sin_codigo`): «no llama» would deny a When that calls a stub, and a profile without `interface_impostor` rejects it too. `a_traves` and `solo_el_valor` get `sin_codigo` as well, and `provocada` its own message. Once the attempts run out, `STUB_LIMITS_NOTE` tells the person the known forms no constant can prove (converting the result, `x not in r`, unpacking). No message asks for a check in a Given (F64 → F63). `lictor.driver.measured.v1` keeps per test `by_constant`, `outcome`, `interface` and `verdict`. The tables of `test_lictor_doubles.py` (89 right and 33 weak ways of checking) fix what C decides of each; a weak one rejected before C, because it passes with None and True, is never accepted.
- **Without a plugin the driver declares its stubs' constants** (ADR-0021, `domain/declared_stubs.py`, `domain/basic_stub_proof.py`). A profile with `oracle.declared_impostors` (`generic@0.2`; never with `impostors`, `Profile` refuses both) asks each stub to fail on a line of its own with Lictor's mark (`STUB_MARK`, `lictor: no implementado`) ending in a comment `lictor-impostor: <A> | <B>` (`IMPOSTOR_MARK`, ` | ` between spaces): two statements that replace the whole line returning two distinct values of its type, none its zero but a boolean's, never null, using only what the signature already uses, or a single one (`return`) for a function without a result; the driver's order says so (`declared_stubs_rule`, `{regla_stubs}`) and `generic.skill.md` gives each language's form (Go: a package sentinel for a function that only returns `error`). `CheckRed._declared_step` (dispatched by `_stub_impostors`) reads every writable file outside the driver in the clean clone (`declared_stubs`), refuses at once the lines written wrong that the driver added (`impostor`, `form_problem_text`; one already in HEAD isn't its), and with no stub seals unchecked (`stub_impostors: 0`, `unchecked_why` `sin_marca` or `sin_marca_con_codigo` when the driver changed code in `paths.writable`). Otherwise it runs the acceptance once per variant (one if every stub has one constant, `single_variant`), each in a clean clone with every stub replaced (`declared_variant`), evidence in `NNN-red/impostor-<n>/`, phase `stubs`: a tampering or a changed environment rejects (`_after_run`, shared with the other impostors), an ambiguous mapping rejects always (`mapeo`, `ambiguous_variant_reason`: a `t.Run` one constant reaches is caught before the seal), and a report that can't be trusted or doesn't map makes that variant not count, with the crash or mapping text (`unjudged_reason`, the compiler included). `basic_proof` judges each new pending test from facts (`VariantFact`: passed, `carries_mark`; a case skipped with a constant counts as not failing with it, or `t.Skip` would leave it unjudged; the red's mark kept as `pending_marked`), in order: a variant still marked → `sigue_sin_implementar`; passes with every one that counts → `sobrevive` (with one not counting, `sin_juzgar`); passes with one and fails with another → `probado`; fails with all → `probado` if its red carried the mark, `sin_stub` (unchecked, `unchecked_why` `sin_stub`) if not. `sobrevive`, `sigue_sin_implementar` and `sin_juzgar` reject, retryable, each with its line (`basic_reason`, `TestRejection` is every rejected verdict), in one rejection (`_declared_rejection`; `BASIC_LIMITS_NOTE` once the attempts run out, only with a `sobrevive`). Each variant file is read and written as bytes, so `\r\n` stays. `report.md` adds to «Cuarentenas» that a quarantined scenario's stubs stay in the branch with the mark (`QUARANTINED_STUBS_NOTE`). `lictor.driver.measured.v1` keeps `declared` per test (`by_variant`: `pasa`, `falla`, `marca`, `no_cuenta`; `outcome`; `verdict`), and «Medidas del driver» shows it for a profile without classes. What the seal left unchecked by the driver's constants warns with ⚠ in `RunProgress` (`seal_warning`), counts in `status`, and `report.md` says why (`unchecked_text`). Rule C and `python-uv` don't change.
- **The driver's commit passes the controls that block every attempt** (G3, ADR-0021). After the red and the impostors, before the seal, `CheckRed._driver_controls` runs on a clean clone of the candidate, inside `IntegritySnapshot` and with `ensure` after, the `attempt` controls in `block` (`driver_controls`, domain `head_controls.py`) through `CheckProject`, as «Los controles pasan en HEAD» does, with every `min_score` dropped (the stubs are uncovered on purpose; the first green meets it), the paths the driver deletes (`deleted`, so a `when_exists` it removed fails as in an attempt) and no API base (an API break of the driver is judged in each attempt, as before). Evidence in `NNN-red/controles/`, phase `controls`. A failure is the rejection `control`, retryable (`driver_control_problem`; `driver_controls_note` once the attempts run out), joined in one rejection with the stubs' impostor's (`_with_controls`, `_joined`, `_JOINED`): two attempts may be all the driver has. A `sin_prueba` of the interface's impostor comes after the controls and stands alone, as does a tampering or a changed environment. A control a right driver can't pass (its own coverage threshold, the length of a stub's line) is exempted by the person with `"driver": false` in its change of `lictor.json` (`checks_driver` in the domain, in the fingerprint); `driver.sealed` lists them in `driver_exempt` and `report.md` names them (`driver_exempt_note`). Lictor's own `coverage-domain` is exempt: its threshold is its own. The driver's order gets `{arreglos}` as the implementer's does: `build_driver` passes the `checks` and the `fixes` apart.
- **Collateral greens skip the agent.** After a passing verification, `collateral_greens` finds the pending scenarios the same tree also makes pass, and `VerifyAttempt` chains an empty commit on the candidate (`commit_tree(parent=..., empty=True)`). `last_verify.candidate` is the head of that chain, so `commit` moves the branch to both at once and marks them all green.
- **Scenarios map to tests by what they executed, or by name.** With `link: "scenario"`, `map_test_cases_to_scenarios` takes the scenario from each case's properties; with `name`, it normalizes `IVA-001` to `iva_001` and looks for it in the test name or classname. Either way it requires exactly one test per scenario, or raises `DriverError`; several cases of one scenario raise `AmbiguousMappingError`, with the scenario and the cases, whose message says a subtest or a parametrized test is another case. `Scenario Outline` is refused at `load_spec`, so a scenario never has several cases of its own. **With the driver sealed they come from what the implementer can't change** (G1 of 0.23.2: a Go `t.Run` after the stub's call is one case at the red and two with the code done, and the mapping is of every scenario, so each spent its attempts): `VerifyAttempt` gives the implementer the facts and both causes (`ambiguous_with_sealed_driver`: rename a test of its own that carries the ID, or leave the driver's alone) and `VerifyResult.ambiguous`; the state keeps, per verification of the implementer **in the whole run**, never per scenario (`ambiguous_scenarios`, `with_mapping`: only a verification that reached the mapping counts), the ambiguous scenario, and when the last `PERSON_ONLY_STREAK` agree on it (`sealed_driver_cases`), `verify` ends the run with 10 (`sealed_driver_reason`). A declared conflict, which goes to quarantine at once, or `max_attempts: 1` can't hide the streak.
- **A person can register what Lictor can't prove.** `lictor register <ID>...` (`RegisterScenarios`) takes the lock, refuses if a run can be resumed, needs a clean tree and an identity, is all or nothing (`registration_problems`), states what is asserted for a new or a reopened scenario and asks (or `--yes`; without a terminal it refuses). It makes one empty commit with a `Scenario:` per scenario and `Lictor-Asserted-By`, never `Lictor-Run`, and emits `scenario.asserted`. `SpecHistory` reads both trailers (`GreenRecord.by_lictor`, `asserted_by`); `spec.loaded` carries each green's commit, and `report.md` and `lictor status` show a green whose commit lacks `Lictor-Run` as registered by hand. Every green Lictor has committed carries `Lictor-Run` since its first version (`b4a603e`). The mark is informative: anyone can write a trailer.
