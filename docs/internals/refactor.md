# The refactor after each green

What the refactor sees, what it may not raise, and where it may work. Part of the reference linked from [AGENTS.md](../../AGENTS.md#how-a-run-works); each point names the code, ADR and finding behind it.

- **A refactor follows each implemented green** (ADR-0010). `route_commit` sends `commit` to `refactor` when `lictor.json` leaves `refactor.enabled` on (the default; `init` doesn't write it, and it is in `config_fingerprint`), and only `commit` goes there: a collateral, a registration or a re-registration changed no code. `RefactorScenario` makes one call in a fresh copy of HEAD, through `AgentTurns` (`usecases/agent_turn.py`, shared with `ImplementScenario`), with `prompts/refactor.md`: the scenario, the paths its green commit changed (`Vcs.changed_paths`), the profile's `refactor_hints` (only in the profile, like `driver_hints`: `Defences.refactor_hints`, and a `lictor.json` with them exits 10, `refactor_hints_message`) and every `agent_run` whose plugin loads, minimum or not (`refactor_measures`). It has one attempt and spends none of the scenario's: a backend that fails pauses or repeats the call (`route_refactor`, as `build_driver`), and `settled_without_verifying` (domain `refactor.py`) ends a call before any verification: `rejected` is discarded, a finished turn with no change is `unchanged`, one cut short with no change is discarded (`L0-sin-cambios`). Any other tree goes to `verify_refactor`, which is `VerifyAttempt` with `role="refactor"`: `L0-sello` too, its candidate is `refactor(<ID>): mejorar el código sin cambiar el comportamiento` with `Lictor-Run` and `Lictor-Refactor-Of` and no `Scenario:` (so `SpecHistory` keeps the green's commit), `acceptance_failure` has no target (only the greens, its own among them), and `refactor_regressions` fails it at `L0-regresión` when a JUnit control passes fewer cases, a scored control leaves more untested, or a complexity control leaves more above its limit, than in the green's verification (`oracle_measures`, kept in the state as `refactor_baseline` by `verify`): without it a refactor could delete the unit tests, since `unit` passes empty and `python-uv`'s coverage only measures. What a score leaves untested is a count (`score_misses`: lines and branches not run, tried mutants not killed), never the percentage: removing covered code lowers the percentage and leaves untested exactly what was, and that is the simplification a refactor is for (F61). The refactor's prompt says what its green left untested (`refactor_measures_text`, from `refactor_baseline`) and what to do if it rises (it split or moved code the green didn't cover: cover it or don't split it), and `python-uv`'s `coverage` measures with `python_uv/lictor_coverage.py`, which counts as `score_misses` and, with the green's report Lictor copies next to it (`coverage-del-verde.json`, from the verification the state names in `refactor_baseline_step`), names where it rose and fell, its counts and the green's on its last line (F71). A pending scenario its tree turns green is a collateral, chained as in an attempt and marked `after_refactor`. `commit_refactor` (`CommitRefactor`, not `CommitGreen`, which would mark the scenario green again) advances with `advance_head` and pauses as `commit` on a blocked branch. A refactor never feeds `failures` or `rejected_paths` and never quarantines. It reuses `attempt_tree` and `last_verify`, so a resume accepts its candidate like an attempt's and its kill points fit the existing classes; the state adds `refactor_of` and `refactor_outcome`. `lictor.scenario.refactored.v1` says `applied`, `discarded` (with `failed_at`) or `unchanged`; `agent.*` carry `role: "refactor"`, `verify.finished` carries `role` for both, and evidence is `NNN-refactor.json` and `NNN-refactor-verify/` beside the green's attempt. `RunProgress`, `status` (`--json` adds `refactor`) and `report.md` (a «Refactor» column, a «Todos los refactors» row, a «Refactors» section, and the role in the deduplication key) count it apart from its scenario.
- **The refactor sees complexity, and may not raise it** (ADR-0013, F60). `python-uv`'s `complexity` control (L1, `measure`, `limit: 10`) runs `python_uv/lictor_complexity.py`, a module of the profile in `verification.files` that reads `src` with `ast` and imports, runs and configures nothing: `uv run python -I -B -m lictor_complexity src --out {out}`. Its definition is Lictor's, fixed by `test_lictor_complexity.py`: 1 plus each `if`/`elif`, ternary, `for`/`while`, `except`, `case` (but a last one that takes anything with no guard), `for` and `if` of a comprehension and operand of an `and`/`or` after the first; nested functions and methods apart, lambdas in their function. It equals radon 6.0.1 and lizard 1.25.0 on every function the passes measured, and not ruff `C901`, which ignores `and`/`or` and adds nested functions to the outer one (Lictor's own `lint` keeps `C901`, so its `src` measures 34 functions above 10 and only records it). The report is every function with its value and its lines, `line` to `end_line` (`ComplexityReport`, `ComplexityReader`; one without `end_line` is invalid); `limit` is the control's, only and always with `report: "complexity"` (a run field, a project decision by `id`), and reaches the verdict through `VerdictRule.limit`: `complexity_verdict` fails naming the functions above it. `over_limit` (domain `complexity.py`) gives `excess` (what they exceed it by, summed) and `peak` (what the worst exceeds it by): `_measure_of` turns them into two `MissKind`s, so `refactor_regressions` discards a refactor that raises either, at `L0-regresión`, and keeps the list in `Measure.findings`. `RefactorScenario` names, from that list in `refactor_baseline`, only the functions with a line its green changed in `{medidas_del_codigo}` (F84, see below) (`refactor_complexity_text`, through `RefactorBlock` of `domain/code_measures.py`, the form both controls of the code share), says when it is empty, and offers the `agent_run` `uv run python -I -B {lictor_files}/lictor_complexity.py src`: `agent_files_dir` copies the profile's files outside the project and the copy for the call, and `{lictor_files}` is written into the command and into the `agent_tools` rule (`agent_tools_with_files`); a call without the copy, as the driver's, drops the rule. The implementer hears of it only when the control blocks (`implementer_complexity_text`). `verify.finished` keeps `complexity: {limit, over, excess, peak}` (`RecordedComplexity`); `report.md` and `check` say it in one phrase (`describe_over`). The repro harness keeps it in the light project: it costs milliseconds and proves measuring runs no project code.
- **The refactor sees duplication, and may not add to it** (ADR-0014, F65). `python-uv`'s `duplication` control (L1, `measure`, no limit) runs `python_uv/lictor_duplication.py`, a stdlib module of the profile in `verification.files` (`tokenize` and `ast`, no project code imported or run, no configuration read), with `uv run python -I -B -m lictor_duplication src --out {out}`. It runs in the project's interpreter, so it stays valid back to Python 3.9 (`from __future__ import annotations`, no PEP 695) and `pyproject.toml` gives ruff `py39` as target for the profile's modules. Its definition is Lictor's, fixed by `test_lictor_duplication.py`: a clone is 50 tokens or more found in two places, in one file or two, with names and literals renamed consistently within each function (`_consistent`, Baker's p-match); comments, layout, imports, signatures and docstrings neither count nor cut; an f-string is one token, its source; a table (a unit shorter than 50 tokens without a statement keyword, repeated for 50 or more: dict entries, fields, keyword arguments) neither counts nor joins; a run that repeats a longer unit counts as its copies; overlapping places are one, so clones come as families. The report gives each file's tokens and the runs in a clone, merged, and each family with its places (file, lines, token run): `DuplicationReport`, `DuplicationReader` (the four JSON readers share `json_report`), and `duplication_report` refuses one whose covered runs aren't exactly the union of its places. `duplication_verdict` fails naming the clones (with `mutation_verdict` and `complexity_verdict` it shares `_own_report`). What the refactor may not raise is `in_clones`, the tokens in a clone, every copy counted (`MissKind` `duplicated`): symmetric, so neither renaming a file nor a local changes it, and neither lines (formatting moves them) nor a percentage (F61). `Measure.findings` keeps `Duplication` (`domain/duplication.py`, every clone: the refactor's scope is drawn from them, and `NAMED` only bounds what is printed), and `RefactorScenario` names in `{medidas_del_codigo}`, after complexity, only the clones with a place on its green's lines (F84), with `in_clones` and the `agent_run` `uv run python -I -B {lictor_files}/lictor_duplication.py src`, whose second line prints that number. `code_controls` gives both controls of the code, and `refactor_measures` leaves them out. The implementer hears of it only when it blocks (`implementer_duplication_text`). `verify.finished` keeps `duplication: {clones, in_clones, code_tokens}` (`RecordedDuplication`); `report.md` and `check` say it in one phrase (`describe_duplication`). Lictor's own `src` measures 18 clones and records them.
- **The refactor stays in what its scenario changed** (F84, amendment of ADR-0010, `domain/refactor_scope.py`). What is asked is by function, where it may work by file, and the guards stay global. `green_scope` (`application/refactor_scope.py`) draws the scope from the green's commit (`refactor_of`, required in both nodes: after a collateral HEAD is an empty commit) and `refactor_baseline`, and both `RefactorScenario` (the prompt) and `VerifyAttempt` (the gate) call it, so what the prompt names is what the gate allows; nothing goes in the state, since git objects don't change. `Vcs.changed_lines(parent, green)` gives every file the green changed and still has, with the spans it added or changed in its own numbering (one diff per file, a literal pathspec; a file with no hunk, as an empty `__init__.py`, is there with none; a hunk that only deletes is the line before it, `hunk_span`). `refactor_scope` names the functions above a limit with a line in a span (`line` to `end_line`; a nested one and the one holding it both) and the clones with a place in one; their other places open their files (`clone_files`). The profile says where the code is and the project adds to it (`code_paths`, `python-uv`: `src/`; `generic` declares none, so the project does; summed, in the fingerprint, amendment of 0.23.0 of ADR-0010; `code_paths_problem` refuses at load none at all, or a `paths.writable` that reaches none of them). `CodePaths` holds them with the project's `code_exclude` (globs over the whole path, `*_test.go`), which only a project whose profile declares no `code_paths` may write (`code_exclude_message`): in Go and Node the unit tests live beside the code, and the refactor may change them as it moves it. One that excludes every file of HEAD under `code_paths` would leave the gate nothing to guard: `doctor` and a new run stop it with ✗ «Rutas de código», exit 10 (`excluded_everything`, judged on HEAD's files because no fixed glob tells `*.go` from `*_test.go`); with no code yet there it is «no comprobado», and `L0-alcance` judges the same on the green's tree, discarding the refactor. Known limits: any file not excluded under `code_paths` (a `README.md`) hides it, and a tree with only the tests there yet is refused. `L0-alcance` (`REFACTOR_SCOPE`, after `L0-rutas`, only for the refactor) discards one that changes, moves or deletes a code file HEAD had (`TreeChange.is_new`, from the old mode of `--raw`) outside the green's files and `clone_files`, naming them, also in `reverted_files`; a new file and anything outside `code_paths` (unit tests) pass. The prompt's rule is `scope_rule` (`{alcance}`), which also says not to make a change that would force touching another code file; what the measures found outside is counted in one line (`outside_scope_text`), and each «Mídela» says the command measures the whole project. `tests/fixtures/refactors_pyverifactu_0_20_0.json` holds the 21 refactors of the 4a pass with the 0.20.0: the gate discards exactly the 9 that left their scenario. Known limit: inside a scenario's file the gate sees nothing. With `format` off, nothing asks to format (F83), so the gate never discards for that.
