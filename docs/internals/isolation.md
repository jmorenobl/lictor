# Isolation, integrity and resume

Where a run, the agent and the verification live, and how tampering and kills are caught. Part of the reference linked from [AGENTS.md](../../AGENTS.md#how-a-run-works); each point names the code, ADR and finding behind it.

- **A run works in a worktree and a branch of its own** (ADR-0005). `lictor run` from a normal checkout (`_execute_run`, `cli.py`) never runs there: `_run_target` holds the checkout's lock just long enough to pick the run to resume from the index or create a new one, and the run itself goes to `_run_here` in the worktree, holding that worktree's lock. A new run gets `lictor/<name>` from `--branch`, or `lictor/<run id>` (`run_branch`, `branch_name_problem`, domain `run_branches.py`); an existing branch or directory exits 10. `add_worktree` (`Worktrees` port, `GitCli`) runs `git worktree add -b` from HEAD with the usual hardening, so no `post-checkout` runs. It lives in `lictor_home()/worktrees/<repo>-<hash of its path>/<name>` (`application/run_index.py`): `LICTOR_HOME`, or `~/.lictor`, per machine and not in `lictor.json`; one under the temporary directory exits 40, because a restart would delete the runs that can be resumed. What isn't committed stays in the checkout, and `run` says so on stderr (`uncommitted_left_out`) instead of demanding a clean tree; `doctor` there shows it as ⚠ (`uncommitted_warns`), and inside a worktree it is still ✗. The checkout keeps only `.lictor/worktrees.json`, written before `git worktree add` (`add_to_run_index`): branch, worktree and run id. It only points. **Where each indexed run stands is decided in the domain from facts read without its configuration** (`domain/run_standing.py`, `bootstrap.run_facts`; G8 of 0.23.2: a worktree half removed had no `lictor.json`, and the error read as «goes on»): whether its directory exists, whether the index marks it `retiring`, whether another process holds its lock (`lock_held`, which creates nothing; `retire`, holding it, passes False), how git knows it, read from the checkout's `<common>/worktrees/*/gitdir` with both ends resolved (`Worktrees.link_of`: `linked`, `unlinked` when git's entry is there but the worktree's `.git` doesn't point back, as after moving the checkout, or `orphan`), and the checkpoint of the run `current_run` names, or the index's id (`checkpoint_state`, orchestration: `get_tuple` on the read-only saver and `exit_code`, no graph; `none`, also for a file without tables, `open`, `finished` or `unreadable`). `run_standing` gives `retiring`, `gone`, `goes_on`, `unlinked`, `not_started`, `finished` or `broken` (orphan, or an unreadable checkpoint). `counts_for_resume` takes `goes_on`, `not_started` and an `unlinked` that hadn't finished, which refuses when chosen with `git -C <checkout> worktree repair <path>` (`unlinked_note`) so `run` never starts another and spends; `resume_choice` resumes the only one, the one `--branch` names, or exits 10 asking for `--branch` among several; `--new` starts another beside them. A `retiring` or `broken` one is never resumed: `run` warns of each on stderr and, when `--branch` names it (with `--new` too), exits 10 with `standing_note`; `status` lists it with that line (`--json`: `standing`, `reason`) instead of failing the whole listing, and `report --branch` exits 10. A run whose worktree lock is held is chosen too, and refused by that lock, with a hint to name a parallel one; probing the lock takes it for an instant. `status` from the checkout shows every indexed run under `Rama lictor/<name> · <worktree>` (`--json`: `{"runs": [...]}`), and `status --branch` and `report --branch` take one through `_indexed_run`, which refuses inside a linked worktree and names the runs it knows. `lictor retire <name>` takes the checkout's lock and then the worktree's, and goes by its standing. It refuses (10) `goes_on` and `unlinked`, touching nothing. A `linked` one (`not_started`, which it no longer refuses: nothing ran there; `finished`; `broken` by its checkpoint) needs a clean tree (10 otherwise), keeps the evidence, **marks the index entry `retiring`** (`mark_retiring`) before the first removal, removes `.lictor/verify-env` with `remove_tree` (G7: Go leaves its module cache read-only, and git couldn't remove it) and then runs `git worktree remove` from the checkout, never `--force`; if git fails (a lock, a submodule) it exits 40 saying `retire` again finishes it. What a failed removal leaves isn't fixed (git stops at the first failure of each directory, in `readdir` order, and still deletes its own entry), so a marked run is a retire halfway whatever its directory looks like: linked, it repeats the removal; forgotten by git, `foreign_leftovers` over `tree_entries_on_disk` allows only `.lictor/`, a `.git` file and the paths of the branch's commit, and with anything else exits 10 naming it (`leftovers_problem`), or else `remove_tree` takes the whole worktree. An `orphan` without the mark (one 0.23.1 left) is looked at before anything goes: only `.lictor/` and a `.git` file, or 10 touching nothing; then its evidence, the mark and `remove_tree`. Git's own entry for a worktree whose directory is gone is dropped with `git worktree remove <path>`, which removes just that one, never `prune` (`_forget_in_git`, also for `gone`: `git branch -d` refuses a branch a worktree of git's still has). Then it drops it from the index (`remove_from_run_index`). Before removing it, `archive_run_evidence` copies the worktree's `journal.jsonl`, `report.md` and `runs/` (never the checkpoint or the seal: the run can't resume any more) to the checkout's `.lictor/retired/<name>-<run id>/` (`retired_name`), through a partial directory renamed into place, keeps one already there (a retire halfway kept it whole), and keeps the `retention.keep_retired` most recent (10, `retired_to_prune`; outside `config_fingerprint`, read from the checkout's `lictor.json` or its default if it doesn't load, `retired_runs_kept`). A copy that fails removes nothing and exits 40 (F56). It deletes the branch only with `--delete-branch` or a yes at a terminal, and then with `git branch -d`, never `-D`: one that isn't integrated stays, with exit 10. `init`, `doctor`, `skill`, `check` and `register` stay in the checkout where they are launched (ADR-0005): `register` moves the person's branch, which a run in its own worktree never anchored (`test_register_in_the_checkout_doesnt_step_on_a_run_in_its_worktree`). Inside a linked worktree, made by hand or by another tool, `run` works there as it is and refuses `--branch`. The run's state, `.lictor/` included, lives in its worktree, where everything below holds unchanged. `GraphContext.result_branch` (the branch of a linked worktree) adds `integration_hint`, with the worktree's path, to the reason of a run that reached the end: integrating it, with a merge or a pull request, is always the person's step.
- **The agent works in a copy, and the project belongs to the user.** Each agent call gets `agent_workspace` (`application/run_files.py`): a fresh export of HEAD outside the project, with no `.git`, no `.lictor/` and no ignored files, gone after the call. `Vcs.capture` reads it into a throwaway index over HEAD, so the result is an exact tree (binaries, modes, deletions), not a textual patch, and `Vcs.changes` and `added_lines` give L0 its diff, with renames split so a move can't hide what it removes. A `.gitignore` in the copy can only hide files from the result, and so can the profile's `gitignore`, which `GitCli` gets from `bootstrap` (`ignored`) and `capture` applies as its `core.excludesFile`, whatever the project's `.gitignore` says: what the profile's tools generate, as the `.coverage` an `agent_run` leaves, never reaches a candidate, and the user's global ignore file isn't read (F59). Nothing in Lictor resets or reverts the project's working tree any more: the only write is `advance_head`, and `Vcs` has neither `reset_to_head` nor `revert_paths` on purpose. A run's attempts never reach the project unless verified.
- **Temporary directories are private.** The copy, the clone and each command's home live under `scratch_dir` (`application/run_files.py`), in `<tmp>/lictor-<hash of the project path>`, outside the project. The name is predictable and `/tmp` is shared on Linux, so the root is created with mode `0o700`, and one that already exists is opened with `O_DIRECTORY | O_NOFOLLOW` and checked on the descriptor: a real directory, not a symlink, owned by the current user, with no write for group or others. Otherwise it exits 40 naming the directory: delete it if it is yours, or point `TMPDIR` to a private one. One that passes but isn't `0o700`, like the `0o755` of older versions, is made private with `fchmod` on the same descriptor: nobody else could have created anything in it, and an unprivileged user can't give a file away. `sweep_scratch` checks the same before deleting anything.
- **One run per worktree at a time.** `lictor run` holds `exclusive_run` (`run_files.py`), a non-blocking `flock` on `.lictor/run.lock`, from before the sweep until it returns: without it a second run swept the first one's copy and clone. A second run exits 10 without writing anything: no `run.stopped`, because the journal and `current_run` belong to the run in progress, which would read any change as tampering. The kernel drops the lock with the process, so a kill leaves nothing behind, and the descriptor isn't inherited, so an orphaned command doesn't keep it. `lictor retire` takes it, in the worktree it removes, after the checkout's; `lictor init` takes it too, because it rewrites `lictor.json`; `register`, because it moves the branch; `check`, because it builds in the temporary directory, which a run starting would sweep; and `doctor`, to build its throwaway environment: if a run holds it, `doctor` checks everything else and leaves the environment «no comprobado». `status` and `report` don't take it: they touch neither the temporary directory nor what `IntegritySnapshot` guards, and only probe it for an instant to tell a run that goes on (`lock_held`, G8 of 0.23.2). The lock file is in neither the snapshot nor the anchor. `own_dir` creates `.lictor/` with a `.gitignore` of `*` before the lock, so git ignores all of it whatever the project's `.gitignore` says (`lictor init` creates it the same way and no longer adds `.lictor/` to the project's `.gitignore`, only the profile's `gitignore` entries, G6): `run` no longer warns that its own lock is uncommitted, a worktree's clean tree doesn't count its checkpoint, and `git worktree remove` without `--force` accepts it (F53).
- **What's verified is what's committed.** After the L0 gates, `VerifyAttempt` builds a candidate commit outside the branch (`commit_tree`) from the captured tree and runs controls and acceptance in a clean clone of it (`verification_tree`). `CheckRed` does the same and seals from the clone. The branch moves with `advance_head`, one `merge --ff-only`: a killed run leaves one state or the other, an edit the commit doesn't touch survives, and one it would overwrite stops with exit 10, resumable through `pause` (`branch_blocked`) with what was verified kept. `Vcs` has no `commit` on purpose, and `commit_tree` refuses a commit that changes nothing unless `empty=True`, which only registrations pass. Re-running `commit` after a crash compares HEAD with the candidate; `CheckRed` compares the `Lictor-Run` trailer and the tree.
- **Every implement attempt starts from HEAD.** `ImplementScenario` verifies the seal and then gives the agent a new copy, so a retry never inherits the previous attempt's edits; only the condensed error carries over. A tampered seal stops before the agent runs.
- **The seal changes who may write what.** `features/` and `paths.driver` are hashed into `.lictor/seal.json` after the red check passes on a fresh driver. Before sealing, the driver role may write them. After, any change fails `L0-sello`. On resume, a changed seal or resolved configuration exits with code 10. `config_fingerprint` (`adapters/config/loader.py`) hashes `lictor.json` merged with its profile plus the content of `verification.files`, so a profile edit counts and a format-only edit of `lictor.json` doesn't.
- **Untrusted commands are wrapped in `IntegritySnapshot`** (`verify_attempt.py`). Agent calls and every control or acceptance command run between `take` and `verify_and_restore`, which restores the state files (the checkpoint with its `-wal`, the journal, the seal, `verify_env.json`, `current_run`, `fake_executor.json`, `lictor.json`) and, given a `Vcs`, HEAD and the repository's control files, and names what changed in `changes`. `-shm` doesn't count: it is the index readers share, and any reader may create or update it. Reading the checkpoint must not touch the rest, so `lictor status` opens it read-only (`read_only_sqlite_saver`, `mode=ro`, no `setup()`, no checkpoint on close): with a connection that may write, closing moved the WAL into the main file and deleted `-wal` and `-shm`, and the attempt in progress failed at `L0-estado` (F13). `report` reads only the journal. Control files go back before any git command runs: no `-c` can name a filter in advance. An agent call that tampered gives the signal `rejected`: the attempt fails at `L0-estado` without verifying, spends the attempt and emits `state.tampered`. The next prompt doesn't list what changed, which the agent never sees: it says the attempt was discarded because the run's state changed outside its copy (`error_for_agent`); `state.tampered` and the evidence keep the names. New code that runs agent or project commands needs the same wrapper, with the `Vcs`.
- **Git runs hardened.** Every call in `GitCli` carries `core.fsmonitor=false` and `core.hooksPath=/dev/null`, ignores replaced objects and drops inherited locations (`GIT_DIR` and the like). `export_tree` and `capture` don't read user configuration either, so a global `core.autocrlf` can't change the tree under test. `export_tree` fetches through `refs/worktree/lictor/verified`, a ref of each worktree, so two runs in two worktrees of one repository never move the same one.
- **The control files include the common directory.** `GitCli` finds the repository by reading, never by asking git: `.git` is a directory, or in a linked worktree a file pointing to `<common>/worktrees/<name>`, whose `commondir` names the common directory. `_control_paths` takes `HEAD` and `config.worktree` from the worktree's directory and `config`, `hooks/` and `info/` from the common one, under the names they have in a normal checkout, plus the two pointers (the `.git` file and `commondir`). In a normal checkout the pointers don't exist, so its fingerprint is the one 0.2.0 computed. `restore` puts the pointers back first, one at a time, and reads every other path again after them, so a redirected `commondir` can't send the rest elsewhere.
- **A resume compares against the anchor.** The checkpoint records HEAD, the hash of `seal.json` and the fingerprint of the repository's control files (`observe_anchor`, set at `preflight`, after sealing and after each commit). `_integrity_refusal` (`cli.py`) compares the fingerprint first, reading bytes without running git, then the rest, and refuses with exit 10, also on uncommitted changes (D4). The anchor carries `format` (`ANCHOR_FORMAT`): one without it was written by 0.2.0, which didn't hash a linked worktree's common directory, and `anchor_from_older_version` refuses it before comparing, with its own message (start over with `--new`), not as tampering. What a crash can legitimately leave is accepted: the candidate of the last verification, the driver's tree before the seal, or, with `red_check` pending, one commit on top of the anchored head with its same tree (`baseline_head_accepted`): the repeated red check tests every green again. It raises the cost of a forgery, it doesn't rule one out: the checkpoint is within reach of the same user.
- **Checkpoints are written synchronously** (`DURABILITY`, `orchestration/graph.py`). With the default, a background thread writes the WAL while the agent runs: a kill loses it, and `IntegritySnapshot` reads it as tampering. Anything that invokes the graph must pass it. It doesn't cover `put_writes`, which LangGraph still leaves to a thread: `preflight` (it builds the verification environment), `build_driver`, `red_check`, `implement`, `verify`, `refactor` and `verify_refactor`, and `load_spec` and `report`, which may end the run and survey what it changed, hold the saver's lock for the whole node (`_holding_checkpoint_writes`), so a write in progress ends before the snapshot and one not started waits. Still under that lock, once the node ends, the saver's connection is closed without folding the WAL and a new one opened (`_reconnected`): the old one kept descriptors to whatever a tampering left, unlinked `-wal` and `-shm` included, read the restored file through them and the run died with `no such table` instead of failing the attempt at `L0-estado` (F19). It stays open during the node on purpose: while it lives, a reader that may write can't be the last connection and fold the WAL when it closes. Python 3.13 shows the race and 3.12 hides it; `test_a_late_checkpoint_write_is_not_tampering` forces it on any version. A new node that runs agent or project code needs the same wrapper, and it can't touch the saver inside: the lock isn't reentrant, so the node would wait for itself forever. Only Lictor's own nodes run there, so that is a programming error for the suite to catch (the global `timeout` turns the hang into a failure with its traceback), not something production patches over. The wrapper relies on `SqliteSaver.lock`, so `langgraph-checkpoint-sqlite` is pinned below 4.
- **`.git/config` is guarded by its keys** (ADR-0022, S22 of 0.25.0). `domain/git_config.py` reads the entries `git config --file <copy> --no-includes --list -z` gives (`_read_config`, `git_cli.py`: on a copy, outside the repository, with no global or system configuration) and calls a key inert when it is in another branch's section, or in the watched branch's but not one git reads (`GIT_BRANCH_KEYS`). A change of only inert keys (an editor's `vscode-merge-base`, the person's `git push -u`) is neither tampering nor restored; a guarded one restores the whole file and is named by its keys, `.git/config (core.hookspath)`, so a test that expects `.git/config` alone after a tampering fails. `fingerprint()` hashes the guarded entries by key, each key's values in order (anchor format `3`): a comment or a moved section changes nothing. A file git can't read as a configuration counts as changed whole.
- **A run's evidence reaches the checkout at every exit** (ADR-0005 amended, S21 of 0.25.0). `_run_keeping` (`cli.py`) copies the journal, the report and `runs/` to `.lictor/retired/<name>-<run_id>/` of the checkout when the run returns, raises or is interrupted, also when it runs inside its own linked worktree (`_indexed`, `Worktrees.main_checkout`); not when another process holds the run. `archive_run_evidence(replace=True)` writes beside and renames into place, moving the older copy aside first; `recover_aside` puts that one back if a replacement stopped between the renames. `retire` replaces the copy too, and of a worktree already gone says where its evidence is or that it was lost (`_tell_evidence_of_gone`).

## Known limitations

a green commit doesn't yet withstand an adversarial agent. It is the exact tree that passed in a clean clone, with no user configuration involved, and the agent no longer works in the project: it gets a copy with no `.git` and no `.lictor/`. That closes the routes that go through the agent's working directory, not the rest: it runs as your user, so with an absolute path it can reach `.git`, `.lictor/`, the verification environment, `~/.netrc` and the interpreter. Those writes are detected and undone while Lictor is alive (`IntegritySnapshot`, the environment hash) and refuse a resume after a kill (the anchor in the checkpoint), unless the checkpoint is rewritten as well. A process the agent leaves behind can plant in the environment between `prepare` and its hash, and the hash then vouches for it (`test_nothing_planted_during_the_build_is_trusted`). Separately, any project code imported during the tests runs in the runner's process, so it can alter the runner as well as forge the report, the properties of the outcome plugin included (`test_c6`). No phase of this plan closes those two: they stay as strict `xfail` until the sandbox of increment 4, and until then a green doesn't withstand an adversary. The `c4` and `c4b` cases only close specific routes: an installed plugin, `src` in the interpreter's startup path (`sitecustomize`), a package in `src` replacing a dependency, and inherited variables. They don't close `c4` in general.

The keys git reads from *another* branch's section (`remote`, `merge`, `mergeOptions`, `rebase`) aren't guarded (ADR-0022): an agent writing `branch.<the person's branch>.remote` by absolute path changes what the person's next `git pull` fetches, and Lictor doesn't undo it. Guarding the checkout's branch too would break the person's own `git push -u` during a run again, which is S22.
