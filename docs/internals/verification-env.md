# The verification environment and the profile

What the verification environment contains, what the profile guarantees and what `lictor.json` may change. Part of the reference linked from [AGENTS.md](../../AGENTS.md#how-a-run-works); each point names the code, ADR and finding behind it.

- **Verification runs in its own environment.** `VerificationEnvironment` builds `.lictor/verify-env` once per run from `verification.prepare` and hashes every file, bytecode included. `ensure` compares the hash before and after the commands: a mismatch fails `L0-entorno`, rebuilds and emits `env.tampered`. A failed `prepare` is exit 40. Commands run through `verification.env`, which in `python-uv` must stop the tool from syncing or creating an environment in the clone and from writing bytecode: dropping any of those variables changes the hash or the tree under test. The project isn't installed in that environment: an editable install would import the agent's tree instead of the clone's. Its metadata is there all the same, in memory and only inside pytest (F82, ADR-0019): see «Project code never enters the interpreter's startup». Autoload is off, and plugins come from what is installed: after `prepare` and before the hash, `plugins_command` asks the environment's own interpreter (`-I -B`) for the `pytest11` entry points without importing them. The list joins the profile's `plugins` in `plugin_variable` and goes to the manifest. `ensure` asks again once the hash matches and compares, and the commands read it from memory, never from the manifest, because project code runs between them. Nothing is discovered at run time. Each entry must be a module: `module:attr` can't be loaded by name and exits 40. Plugins register under their module name, so `-p no:<name>` only blocks one whose module is `<name>` or `pytest_<name>`. What Lictor removes of its own goes through `remove_tree` (`run_files.py`): `rmtree` with an `onexc` that gives write permission back to the directory in the way, only `root` and what is inside it, never its parent, and tries each path once more; it never follows a link, and what still can't go raises `CleanupError` (40). `_build` and `retire` use it; `sweep_scratch` too, as a courtesy that leaves what can't go (an orphaned process still writing). `VERIFY_ENV_DIR` names the environment's directory for both.
- **Project code never enters the interpreter's startup.** `PYTHONPATH` must not name the tree under test: it would run `sitecustomize` in every Python tool, `mypy` included, and pytest's `pythonpath` isn't a substitute, because pytest applies it before importing `PYTEST_PLUGINS`, so `src` could replace a dependency. `python-uv` fixes `PYTEST_ADDOPTS="-o pythonpath="`, which also voids what the project's `pyproject.toml` declares, and `verification.files` copies a plugin (`profiles/python_uv/lictor_project_path.py`, a real module that imports nothing of Lictor) into the hashed environment, in the directory the environment's own interpreter reports (`files_dir_command`, with `-I` for isolation and `-B` because `-I` ignores `PYTHONDONTWRITEBYTECODE`; never `-S`, because `site` is what activates the venv). It appends `src` in `pytest_load_initial_conftests`: after startup, after the plugins, and behind `site-packages`. It also appends, after `src`, the `pythonpath` the project declares, read from the file pytest chose (`config.inipath`, with its documented format, never pytest's private reader), so tests importing from `tests/support` still find it (F77); a path outside the tree stops the suite saying so. Then it registers, at the end of `sys.meta_path`, the project's own distribution (`register_metadata`, F82, ADR-0019): `python_uv/lictor_metadata.py`, a stdlib module of the profile in `verification.files` valid back to 3.9, reads the clone's `pyproject.toml` without running anything (name; a static version, or a dynamic one a backend leaves in a literal: hatch `path`/`pattern`, setuptools `attr`/`file`, flit; normalized with `packaging`; `[project.scripts]`, `gui-scripts` and `entry-points` but `pytest11`), only when uv would install the project (`[build-system]` and `tool.uv.package` not `false`, or `true`), never over a distribution already found (so a nested `pytest.main` adds no second finder), only to a search that looks at the project's `src`, and a distribution of the library whose `Context` asks (the backport `importlib_metadata` gets its own class). A version from git registers nothing, and the reading never raises: what it can't read is a reason. The survey reports the same reading (`metadata`: `{name, version, groups, unread}`, `{not_installed}` or `{problem, fix}`, `ProjectMetadata`), and `metadata_facts` (domain `blind_spots.py`) turns it into «Dependencias de la verificación»: ✓ with the name, version and groups, or with «sin metadata del proyecto» for a project uv wouldn't install (`PreconditionCheck.detail`, printed beside the warnings), or ⚠ with the reason, never ✗; `run.started` keeps that check's warnings in `dependencies` and `RunProgress` prints them. A subprocess without pytest (`python -c`) sees neither `src` nor the metadata. In `pytest_addhooks` it blocks pytest 7/8's `python_path` plugin (its only work is what `-o pythonpath=` voids, and it fails an assertion with no configuration file before 8.1) and marks every plugin of `PYTEST_PLUGINS` not yet imported for rewriting, as autoload does: otherwise `xdist.looponfail` imports `xdist.plugin` before its turn, pytest warns, and a project with `filterwarnings = ["error"]` can't start (F81). `test_lictor_project_path.py` fixes the matrix; it was checked on pytest 7.4 to 9.0 and Python 3.9. Tools that need the project on the path get it the same way, after starting and at the end: `scripts/check_architecture.py` appends `src` and then calls Import Linter. It must not run from `src`: Import Linter puts its working directory first, so a `src/typing_extensions.py` would run inside the control and could exit 0 over a broken contract.
- **Verification starts from an empty environment.** `verification.inherit` lists the exact names that pass, and `env` then fixes values, so `env` wins and whatever nobody listed stays out. `command_env` returns the whole environment and `CommandRunner.run` uses it as given: `env=None` inherits, anything else replaces. A missing variable breaks visibly (a tool that isn't found fails `prepare` with exit 40). This covers verification, `lictor check` included; only the agent's commands keep the caller's environment.
- **Each command has an empty home of its own.** `{home_dir}` in `env` is a new directory per command, outside the project, so no user configuration decides a control (a permissive `~/.config/ruff/ruff.toml` gave 3 false greens) and nothing one command writes there configures the next. The real `~/.config/...` isn't read even if project code writes to it, because `HOME` points elsewhere.
- **`prepare` doesn't share its environment with the commands.** Network settings and credentials pass through `prepare_inherit`, which the commands never see. It has an empty home too, so what it needs from the real one is explicit: `prepare_ask` asks the tool with the caller's environment (`UV_PYTHON_INSTALL_DIR`: without it `uv` silently picks another interpreter) and `prepare_home_files` points to a file there (`NETRC`, `~/.netrc`), unless the variable is inherited. `prepare` runs `--no-cache`: a poisoned entry of the shared cache reached the environment and the hash vouched for it, and `--refresh` doesn't help, so every build downloads against the hashes of `uv.lock`. No network means exit 40. Repro cases use the shared cache through a copy of the profile; `make_project(downloads=True)` keeps the real one.
- **The profile owns what verification guarantees, in three classes** (ADR-0020). The project writes what the profile doesn't declare and only adds to what it does. **Summed** (profile + project, in that order, without duplicates: one more only rejects more): `suppressions`, `banned_patterns` (regexes validated in `LictorFile` too), `forbidden_paths`, `code_paths`, and `verification.env`, `inherit` and `prepare_inherit`. **Exclusive**, written by the project only where the profile declares none, or exit 10 with its own message (`_reject_exclusive_fields`, checked on the raw file once the profile is known, before validating): `verification.prepare` (`prepare_message`: the profile's is the contract of the hashed environment), `acceptance.driver_hints` (`driver_hints_message`, which sends the project's own to `hints`) and `code_exclude` (only without the profile's `code_paths`). **Only the profile's**, never written by a project even when the profile declares none, each refused with one sentence (`profile_only_message`, «solo lo declara el perfil»), never pydantic's, the list taken from the models (`_PROFILE_ONLY_FIELDS`, `_PROFILE_ONLY_VERIFICATION`): the oracle, `survey`, `acceptance.needs_plugins`, `files`, `plugins`, `plugins_command`, `plugin_variable`, `files_dir_command`, `reserved`, `prepare_ask`, `prepare_home_files`, `driver_exempt_paths`, `refactor_hints`, `rule_files` and `hint_values`. `resolve_defences` (`adapters/config/loader.py`) joins them (`_union`) on every load, `LictorConfig` carries the project's, and `driver_hints` reaches the prompt as `Defences.driver_hints`, inside `config_fingerprint`. A profile may leave out `paths`, `acceptance` and `detect`: `generic@0.1` (`status: "alpha"`, never detected, `detect: []` skipped by `_detects`) declares none, nor `code_paths`, and a `lictor.json` without them exits 10 naming every one at once (`missing_project_fields_message`); `init --profile generic` writes the four usual keys and says on stdout what is left (`ProfileInitConfig.to_write`, `status`). A profile can't declare `oracle.impostors` without `red_kinds`: without the plugin's properties they reject right tests too. The profile's `hints` is a template: each `{name}` in `hint_values` is read from a project file (`requires-python` from `pyproject.toml`) by `render_hints`, when `init` writes it and when `lictor.json` leaves `hints` to the profile, with the profile's default if it can't be read. Naming in `verification.env`, `inherit` or `prepare_inherit` a variable the profile fixes, inherits or reserves exits 10. A case that must prove it doesn't depend on a heuristic relaxes it in a copy of the profile (`allowed_paths` in `make_project`), never in `lictor.json`. `paths.protected` stays a project decision, so `uv.lock` is also in `forbidden_paths`: what the lock installs loads as a plugin, so its defence can't depend on `paths`. `UV_*` is reserved because those variables decide where the environment lives, whether `uv` may sync it and where code is downloaded from; a private index authenticates through `~/.netrc` or `NETRC`, not `UV_INDEX_*`.
- **`lictor.json` holds what the person decides.** `lictor init` writes only `version`, `profile`, `backend.model` and `hints` (`_init_payload`); the rest comes from the profile on every load (`_merge_profile_defaults`), so a fix to the profile reaches a project without editing it. The file is validated first as `LictorFile` (what a person writes, which is also what the schema describes) and then resolved into `LictorConfig`. A key written replaces the profile's whole, except `controls`, which are `ControlChange`s by `id` (`_resolve_controls`): one with a profile `id` changes only the fields written (in `model_fields_set`, a written null included) and `enabled: false` drops it, with nothing else written beside it; another `id` adds a control, and goes after the change written before it, or at the end if it is the first. Which shape a change leaves is resolved before pydantic (`resolve_shape`, the table of ADR-0008, point 2), so each mistake has its own message: a control runs a command (`run`, and `level` and `report` to add one) or reads the run of another (`reads` and `adds`, `report: "coverage"`, and none of `empty_exit_codes`, `timeout_s` or `when_exists`); writing `run` over a reader makes it run, and writing `reads` and `adds` over one that runs makes it read. `run`, `reads` and `adds` may be left out but never null. Dropping an `id` the profile lacks is a typo and exits 10, naming the profile's ids. An empty list no longer means «no controls». The profile is `python-uv@0.2`: `@0.1` exits 10 with what changed, from the profile's `retired_versions`, so the full copies 0.2.0 wrote (`tests/fixtures/lictor_0_2_0.json`) no longer load.
- **`forbidden_paths` and `banned_patterns` are heuristics of the profile.** The first are matched against each path component, ignoring case (on macOS `claude.md` opens as `CLAUDE.md`), and rejected in `L0-rutas`, along with any symlink. In the driver's own paths only what `driver_exempt_paths` names is allowed (`conftest.py`): the driver is sealed and committed, so a `tests/acceptance/CLAUDE.md` would plant as well as one in `src/`. Besides the Python configuration, `python-uv` lists what makes another tool run code or follow instructions from the tree it opens: `.claude`, `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `.mcp.json`, `.vscode` and `.github`. At the root they were already outside `paths.writable`; the entries cover them anywhere below. The second are case-insensitive regexes, in `L0-supresiones`. For the implementer and the refactor the suppressions of the added lines must fit in those of the removed ones, across the whole change, each counted by its exact text from where it matches to the line's end (`suppressions_not_moved`, `Vcs.removed_lines`; F72): moving a function with its `noqa` to another module, renaming, reindenting or joining equal ones passes, adding one or changing its text doesn't. The rule over added lines (`suppression_matches`) judges what a fresh driver adds (`CheckRed`, rejection `L0-supresiones`, before running anything): the driver is sealed and never judged again, so a `# noqa` or a `sys.path.insert(0, src)` it leaves stays for every attempt (F12). `python-uv` bans changing `sys.path` (insert, append, slice or reassign; reading it is fine): `src` goes behind the dependencies on purpose, and in front it can replace one. A sealed driver isn't checked. They are heuristics: they raise the cost of cheating, they don't close it. `sitecustomize.py` and `usercustomize.py` are listed as an extra defence; what keeps them from running is the startup path.
- **The acceptance is marked, and pytest-timeout doesn't cut it** (S10 of 0.25.0). Every run of the acceptance (`VerifyAttempt`, `CheckRed`, `CheckProject`) gets `ACCEPTANCE_ENV` (`LICTOR_ACCEPTANCE=1`, `domain/rules.py`), and no other command does: `EnvironmentRunner.run` passes on only `LICTOR_*` variables as `extra_env`. The profile's `lictor_outcome` returns True from `pytest_timeout_set_timer` and `pytest_timeout_cancel_timer` there, so a project's `timeout` can't turn a slow scenario into a valid red; Lictor's own timeout cuts the suite.
- **`lictor_with_src` runs a tool that imports the project outside pytest** (S19 of 0.25.0). `python -I -B -m lictor_with_src <tool> …` appends `src` at the end of `sys.path` and runs the tool's console script, behind the dependencies as ADR-0019 wants; it is one more of the profile's modules, so it follows the Python 3.9 rule. `doctor` warns of an installed plugin that changes a run of the tests (`plugins_noted`, `noted_plugins`).
